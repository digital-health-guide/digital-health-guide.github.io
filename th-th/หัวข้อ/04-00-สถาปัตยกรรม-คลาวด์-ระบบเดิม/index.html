หัวข้อ 4.0 — สถาปัตยกรรมเทคนิค คลาวด์ และระบบเดิม

ในด้านสุขภาพและการดูแล สถาปัตยกรรมเทคนิคเป็นการตัดสินใจด้านความปลอดภัยทางคลินิก ความมั่นคงปลอดภัย และเงินสาธารณะที่ทำล่วงหน้าหลายปี แพลตฟอร์มที่คุณสร้างขึ้นและระบบเดิมที่คุณปล่อยทิ้งไว้ ตัดสินอย่างเงียบ ๆ ว่าการดูแลจะปลอดภัย เชื่อมโยงกัน และจ่ายไหวได้หรือไม่ นานหลังจากผู้ที่เลือกสิ่งเหล่านั้นย้ายไปทำที่อื่นแล้ว

ทำไมเรื่องนี้จึงสำคัญในด้านสุขภาพและการดูแล#

สถาปัตยกรรมคือชุดทางเลือกเชิงโครงสร้างที่ใช้ได้นานซึ่งอยู่ใต้บริการดิจิทัลของคุณ ได้แก่ อะไรทำงานที่ไหน ส่วนประกอบเชื่อมต่อกันอย่างไร สร้างหรือซื้ออะไร และคงสิ่งใดจากอดีตไว้ ทางเลือกเหล่านี้ผู้ป่วยหรือบุคลากรทางคลินิกแทบไม่เห็น และคณะกรรมการแทบไม่ตื่นเต้น แต่มันกำหนดรูปร่างของทุกสิ่งที่อยู่ด้านบน ระบบที่ออกแบบสถาปัตยกรรมดีทำให้คุณเพิ่มบริการใหม่ได้เร็ว แบ่งปันข้อมูลได้อย่างปลอดภัย และกู้คืนได้เร็วเมื่อมีอะไรพัง ส่วนระบบที่ออกแบบไม่ดีทำให้ทุกการเปลี่ยนแปลงช้า ทุกการเชื่อมต่อเปราะบาง และทุกเหตุการณ์แย่ลง

ในด้านสุขภาพและการดูแล เดิมพันสูงเพราะระบบมีผลลัพธ์ตามมาอย่างมาก เมื่อระบบบริหารผู้ป่วยที่เก่าล้มเหลว รถพยาบาลต้องเบี่ยงเส้นทางและคลินิกต้องยกเลิกนัด เมื่อระบบปฏิบัติการที่ไม่ได้รับการสนับสนุนถูกโจมตี บันทึกที่เป็นความลับถูกเปิดเผยและบริการหยุด ดังที่ NHS ได้เรียนรู้ในปี 2017 เมื่อการโจมตีด้วยแรนซัมแวร์ WannaCry แพร่ผ่านเครื่องที่ใช้ซอฟต์แวร์ซึ่งไม่อาจอุดช่องโหว่ได้อีกต่อไป การหยุดชะงักนั้นไม่ใช่การโจมตีที่ชาญฉลาดและเจาะจงเป้าหมาย แต่เป็นผลที่คาดเดาได้จากหนี้ทางเทคนิคที่สะสมในระบบสำคัญ การตัดสินใจด้านสถาปัตยกรรมจึงเป็นการตัดสินใจด้านความปลอดภัย ไม่ว่าจะมีใครมองเช่นนั้นหรือไม่

มันยังเป็นการตัดสินใจด้านความเท่าเทียมและความไว้วางใจ ระบบเดิมที่แบ่งปันข้อมูลไม่ได้ทำให้ผู้ป่วยที่ซับซ้อนที่สุด คือผู้ที่เกี่ยวข้องกับหลายบริการ มีบันทึกที่กระจัดกระจายที่สุด แพลตฟอร์มปิดที่ผูกคุณไว้กับผู้จัดหารายเดียวดูดเงินที่ควรใช้จ่ายเพื่อการดูแล และประชาชนคาดหวังอย่างสมเหตุสมผลว่า NHS ควรทำงานบนเทคโนโลยีที่ทันสมัย ปลอดภัย และดูแลอย่างดี ช่องว่างระหว่างความคาดหวังนั้นกับระบบจริงคือความเสี่ยงต่อความไว้วางใจในตัวมันเอง

สุดท้าย นี่คือที่ที่เงินสาธารณะจำนวนมากถูกผูกมัดไว้เป็นเวลานานมาก ส่วนที่แพงที่สุดของระบบมักไม่ใช่การซื้อ แต่คือทศวรรษของการโฮสต์ การออกใบอนุญาต การบำรุงรักษา และการแทนที่ในที่สุดที่ตามมา ผู้นำที่ถือว่าสถาปัตยกรรมเป็น "เรื่องที่ทีมเทคนิคจัดการ" กำลังมอบหมายภาระผูกพันทางการเงินที่ใหญ่และยาวนานที่สุดบางส่วนขององค์กร หัวข้อนี้เขียนขึ้นเพื่อให้คุณทำให้การตัดสินใจเหล่านั้นต้องรับผิดชอบได้โดยไม่ต้องเป็นวิศวกร

แนวคิดหลัก#

สถาปัตยกรรมองค์กร (Enterprise architecture) คือวินัยในการจัดแนวกระบวนการทางธุรกิจ สารสนเทศ แอปพลิเคชัน และเทคโนโลยีขององค์กรให้สนับสนุนยุทธศาสตร์อย่างสอดคล้อง แทนที่จะเติบโตโดยบังเอิญ มองภาพทั้งองค์กร ได้แก่ ต้องการขีดความสามารถใด ระบบใดให้ขีดความสามารถเหล่านั้น และช่องว่างกับความซ้ำซ้อนอยู่ที่ใด สถาปัตยกรรมโซลูชัน (Solution architecture) เป็นวินัยระดับโครงการที่แคบกว่า ว่าด้วยการออกแบบว่าบริการเฉพาะจะถูกสร้างและเข้ากับระบบโดยรวมอย่างไร ทั้งสองอยู่ในแนวคิดที่กว้างกว่าคือ สถาปัตยกรรมระบบ (systems architecture) ซึ่งเป็นแบบจำลองเชิงโครงสร้างว่าส่วนประกอบ ส่วนติดต่อ และพฤติกรรมรวมกันเป็นระบบที่ทำงานได้อย่างไร ผู้นำไม่จำเป็นต้องลงมือปฏิบัติวินัยเหล่านี้ แต่ควรยืนกรานให้มีอยู่ เพราะการไม่มีมันคือวิธีที่ระบบกลายเป็นสิ่งที่จัดการไม่ได้

สถาปัตยกรรมได้รับการชี้นำด้วยหลักการสถาปัตยกรรม (architecture principles) ซึ่งเป็นชุดข้อความสั้นที่ตกลงกันไว้ เช่น "นำกลับมาใช้ก่อนซื้อ ซื้อก่อนสร้าง" หรือ "สร้างตามมาตรฐานเปิด" ที่ทำให้การตัดสินใจที่สม่ำเสมอเป็นไปได้โดยไม่ต้องยกระดับทุกทางเลือก หลักการถูกบังคับใช้อย่างเบา ๆ โดยคณะกำกับการออกแบบ (design authority) ซึ่งเป็นกลุ่มเล็กที่ทบทวนการตัดสินใจทางเทคนิคที่สำคัญ คณะกำกับการออกแบบในแบบที่ดีเป็นผู้เอื้ออำนวยมากกว่าขัดขวาง มีไว้เพื่อป้องกันอันตรายและความซ้ำซ้อนที่หลีกเลี่ยงได้ ไม่ใช่ทำให้ทีมช้าลงหรือเป็นด่านตรวจเพื่อตัวมันเอง

คลาวด์คอมพิวติ้ง (Cloud computing) คือการให้บริการการประมวลผล ได้แก่ เซิร์ฟเวอร์ พื้นที่จัดเก็บ ฐานข้อมูล เครือข่าย เป็นบริการตามความต้องการผ่านอินเทอร์เน็ต แทนที่จะมาจากฮาร์ดแวร์ที่คุณเป็นเจ้าของในอาคารของคุณเอง คลาวด์สาธารณะดำเนินการโดยผู้ให้บริการบุคคลที่สามและใช้ร่วมกันระหว่างลูกค้าจำนวนมาก คลาวด์ส่วนตัวใช้เฉพาะองค์กรเดียว คลาวด์ไฮบริดรวมทั้งสองอย่าง โดยมักคงบางภาระงานไว้บนโครงสร้างพื้นฐานเดิมขณะย้ายส่วนอื่นออก รัฐบาลหลายแห่ง รวมถึงของสหราชอาณาจักร ได้นำนโยบาย "คลาวด์ก่อน" (cloud-first) มาใช้ หมายความว่าทีมควรพิจารณาคลาวด์สาธารณะก่อนทางเลือกอื่นและต้องให้เหตุผลหากไม่ใช้ เนื่องจากคลาวด์คิดเงินตามการใช้ ไม่ใช่ซื้อครั้งเดียว การควบคุมรายจ่ายนั้นจึงกลายเป็นวินัยเฉพาะ คือ FinOps ซึ่งเป็นแนวปฏิบัติที่นำวิศวกรรมและการเงินมาไว้ด้วยกัน เพื่อให้ทีมมองเห็นและรับผิดชอบต่อต้นทุนที่แท้จริงของการใช้คลาวด์ ในชั้นแอปพลิเคชัน ซอฟต์แวร์เป็นบริการ (software as a service: SaaS) ส่งมอบแอปพลิเคชันสำเร็จรูปผ่านเว็บที่ผู้จัดหาโฮสต์และดูแล คุณจึงตั้งค่าแทนที่จะเดินระบบเอง โครงสร้างพื้นฐานและการโฮสต์ ซึ่งเป็นที่ที่ระบบของคุณทำงานทางกายภาพและวิธีที่ทำงาน อยู่ใต้ทั้งหมดนี้ และมีต้นทุนคาร์บอนเพิ่มขึ้นเรื่อย ๆ ซึ่งควรอยู่ในการตัดสินใจ (ดูหัวข้อ 8.5 — ความยั่งยืนและเน็ตซีโร)

ระบบเดิม (legacy system) คือระบบที่เก่าแต่ยังต้องพึ่งพา เปลี่ยนแปลงยาก และมักใช้ซอฟต์แวร์ที่ไม่ได้รับการสนับสนุนซึ่งไม่ออกแพตช์ความมั่นคงปลอดภัยอีกต่อไป ระบบเดิมสะสมเป็น หนี้ทางเทคนิค (technical debt) ซึ่งเป็นต้นทุนในอนาคตของทางเลือกที่ทำเพื่อความสะดวกในอดีต หนี้เล็กน้อยเป็นเรื่องปกติและแม้แต่สมเหตุสมผล แต่หนี้ที่ไม่ได้บริหารในระดับใหญ่กลายเป็นภาระด้านความปลอดภัยและความมั่นคงปลอดภัย เพราะระบบที่คนส่วนใหญ่พึ่งพากลายเป็นระบบที่ไม่มีใครกล้าแตะ การบริหารเรื่องนี้เป็นงานของ การบริหารพอร์ตโฟลิโอแอปพลิเคชัน (application portfolio management) คือการเก็บบัญชีรายการแอปพลิเคชันทุกตัวอย่างชัดเจน พร้อมต้นทุน สภาพ และคุณค่าทางธุรกิจ เพื่อให้คุณปรับระบบให้สมเหตุสมผลได้ ได้แก่ ยกเลิก แทนที่ หรือรวมระบบ และปลดระวางอย่างปลอดภัยแทนที่จะปล่อยของเก่าทำงานเงียบ ๆ ต่อไป

ระบบสมัยใหม่ถูกยึดเข้าด้วยกันด้วย ส่วนต่อประสานโปรแกรมประยุกต์ (application programming interfaces: APIs) ซึ่งเป็นส่วนต่อประสานที่กำหนดไว้ที่ระบบหนึ่งเสนอขีดความสามารถแก่อีกระบบหนึ่ง API ที่ออกแบบดีช่วยให้คุณประกอบแพลตฟอร์ม ซึ่งเป็นบริการที่นำกลับมาใช้ได้ที่หลายทีมสร้างต่อยอด ขณะที่รักษาส่วนประกอบให้เชื่อมโยงกันอย่างหลวมและเปลี่ยนแทนได้ วินัยที่มีประโยชน์ในที่นี้คือ "แพลตฟอร์มบางที่สุดที่ใช้งานได้" (thinnest viable platform) คือสร้างเฉพาะขีดความสามารถร่วมที่ช่วยลดงานของผู้อื่นจริง และไม่เกินนั้น ที่รองรับการออกแบบอย่างปลอดภัยคือ ปลอดภัยโดยการออกแบบ (secure by design) หลักการที่ว่าความมั่นคงปลอดภัยถูกสร้างไว้ตั้งแต่ต้นแทนที่จะเติมทีหลัง และกรอบทางการเงินสำหรับทั้งหมดคือ ต้นทุนรวมของความเป็นเจ้าของ (total cost of ownership: TCO) ซึ่งเป็นต้นทุนตลอดอายุของระบบ ไม่ใช่ราคาซื้อ เป็นเลนส์ที่ใช้ตัดสินทางเลือกสร้าง/ซื้อ/ตั้งค่า และความเสี่ยงของ การผูกติดกับผู้ขาย (vendor lock-in)

แนวปฏิบัติที่ดี#

  1. ตกลงชุดหลักการสถาปัตยกรรมสั้น ๆ และใช้ตัดสิน เขียนหลักการที่ชัดเจนและจำง่ายไม่กี่ข้อ ได้แก่ นำกลับมาใช้ก่อนซื้อ ซื้อก่อนสร้าง สร้างตามมาตรฐานเปิด คลาวด์ในที่ที่เหมาะสม ปลอดภัยโดยการออกแบบ ออกแบบเพื่อเส้นทางการดูแลทั้งหมด และให้ทีมตัดสินใจส่วนใหญ่ด้วยตนเองโดยใช้หลักการเหล่านั้น หลักการใช้ได้ผลก็ต่อเมื่อถูกใช้พูดว่าใช่และไม่ใช่จริง และมีน้อยพอที่จะจำได้ เรื่องนี้เชื่อมโยงโดยตรงกับหัวข้อ 1.1 — แบบจำลองการดำเนินงาน และหัวข้อ 1.2 — ยุทธศาสตร์ดิจิทัลและการจัดทำแผนที่นำทาง ซึ่งกำหนดทิศทางที่หลักการรับใช้

  2. ดำเนินคณะกำกับการออกแบบที่เอื้ออำนวยมากกว่าขัดขวาง จัดตั้งกลุ่มเล็กอาวุโสข้ามสาขาวิชาเพื่อทบทวนการตัดสินใจทางเทคนิคที่สำคัญ คือที่มีค่าใช้จ่ายสูง ย้อนกลับยาก กระทบหลายบริการ หรือมีความเสี่ยงด้านความปลอดภัยและความมั่นคง ให้ช่องทางที่เร็วและเบาเพื่อไม่ให้ทางเลือกประจำถูกลากผ่านกลุ่มนี้ และให้ยึดมาตรฐานบริการ คือควรช่วยให้ทีมหาคำตอบที่ดี ไม่ใช่เพียงปฏิเสธ คณะกำกับการออกแบบที่กลายเป็นคอขวดจะถูกเลี่ยง และสถาปัตยกรรมเงาแย่กว่าไม่มีเลย

  3. นำคลาวด์มาใช้อย่างตั้งใจ ทีละภาระงาน ไม่ใช่เป็นสโลแกน ถือว่า "คลาวด์ก่อน" เป็นค่าเริ่มต้นที่ต้องใช้เหตุผล ไม่ใช่คำสั่งให้ย้ายทุกอย่าง ประเมินแต่ละภาระงานในด้านความเหมาะสม ที่ตั้งของข้อมูล (data residency) ความยืดหยุ่น ต้นทุนในระดับใหญ่ และความพยายามในการย้าย และยอมรับตรงไปตรงมาว่าการยกแอปพลิเคชันเดิมที่ไม่เปลี่ยนแปลงไปวางบนคลาวด์ (lift-and-shift) มักเพียงย้ายปัญหาไปด้วยต้นทุนที่สูงกว่า ชั่งน้ำหนักมิติคาร์บอนอย่างชัดเจน เพราะที่ตั้งและวิธีโฮสต์ส่งผลต่อการปล่อยก๊าซ (ดูหัวข้อ 8.5 — ความยั่งยืนและเน็ตซีโร) และออกแบบเพื่อความย้ายได้ (portability) เพื่อให้การย้ายระหว่างผู้ให้บริการในอนาคตยังเป็นไปได้

  4. ดูแลพอร์ตโฟลิโอแอปพลิเคชันที่เป็นปัจจุบัน และบริหารหนี้ทางเทคนิคเป็นความเสี่ยงที่มีชื่อ เก็บบัญชีรายการแอปพลิเคชันทุกตัวที่ถูกต้อง พร้อมเจ้าของทางธุรกิจ ต้นทุน ความสามารถในการสนับสนุน และความเสี่ยงที่มี และทบทวนสม่ำเสมอ นำหนี้ทางเทคนิคและซอฟต์แวร์ที่ไม่ได้รับการสนับสนุนขึ้นทะเบียนความเสี่ยงขององค์กรด้วยความจริงจังเท่ากับความเสี่ยงทางคลินิกหรือการเงิน เพราะมันคือสิ่งนั้น สิ่งที่คุณมองไม่เห็นคุณก็ไม่อาจสนับสนุนงบประมาณ จัดลำดับความสำคัญ หรือปลดระวางอย่างปลอดภัยได้ และระบบที่ไม่เคยทำบัญชีรายการคือระบบที่ล้มเหลวโดยไม่มีสัญญาณเตือน

  5. ปรับระบบให้สมเหตุสมผลและปลดระวางอย่างปลอดภัย ยกเลิกระบบที่ซ้ำซ้อน ล้าสมัย และสิ้นอายุอย่างจริงจังแทนที่จะปล่อยไว้ "เผื่อเอาไว้" เพราะทุกระบบที่ยังทำงานคือพื้นผิวการโจมตี ต้นทุนใบอนุญาต และภาระการบำรุงรักษา การปลดระวางเป็นโครงการในตัวมันเอง ได้แก่ ย้ายหรือเก็บถาวรข้อมูลภายใต้กฎการเก็บรักษาที่ชัดเจน ยืนยันว่าไม่มีสิ่งใดยังพึ่งพาระบบ สื่อสารกับผู้ใช้ และตรวจสอบก่อนปิด หากทำดี การปรับให้สมเหตุสมผลช่วยปลดปล่อยเงินและลดความเสี่ยง หากทำสะเพร่า จะทำลายบันทึกหรือทำให้การพึ่งพาที่ไม่มีใครบันทึกไว้พัง

  6. ให้ความสำคัญกับมาตรฐานเปิด API และส่วนประกอบที่เชื่อมโยงกันอย่างหลวม ออกแบบให้ขีดความสามารถถูกเปิดผ่าน API ที่บันทึกไว้และมีเวอร์ชัน เพื่อให้เปลี่ยนส่วนประกอบหนึ่งได้โดยไม่ต้องสร้างทุกอย่างรอบข้างใหม่ นี่คือรากฐานด้านสถาปัตยกรรมของการทำงานร่วมกันที่กล่าวถึงในหัวข้อ 4.3 — การทำงานร่วมกันและมาตรฐานข้อมูล และเป็นแนวป้องกันหลักของคุณต่อการผูกติด มันมีต้นทุนเพิ่มเล็กน้อยล่วงหน้าเมื่อเทียบกับการเชื่อมต่อตรงแบบฮาร์ดไวร์ และคุ้มค่าตอบแทนหลายเท่าในครั้งแรกที่คุณต้องเปลี่ยนผู้จัดหาหรือเพิ่มบริการ

  7. สร้างแพลตฟอร์มที่บางที่สุดที่ใช้งานได้ และไม่เกินนั้น เมื่อสร้างแพลตฟอร์มร่วมให้ผู้อื่นสร้างต่อยอด ต้านทานความอยากทำให้ครอบคลุมตั้งแต่วันแรก ให้ขีดความสามารถนำกลับมาใช้ได้ที่เล็กที่สุดที่ช่วยลดงานของทีมจริง พิสูจน์ว่ามีการใช้งาน และขยายตามอุปสงค์จริง แพลตฟอร์มที่สร้างเกินจะกลายเป็นระบบเดิมของตัวเอง ได้แก่ แพง แข็งทื่อ และถูกเกลียด ขณะที่แพลตฟอร์มบางที่ดำเนินงานดีได้รับการนำไปใช้และพัฒนาตามความต้องการ

  8. ทำให้สถาปัตยกรรมความมั่นคงปลอดภัยและปลอดภัยโดยการออกแบบเป็นเรื่องต่อรองไม่ได้ นำความคิดด้านความมั่นคงปลอดภัยเข้าสู่การออกแบบตั้งแต่ร่างแรก ไม่ใช่ด่านก่อนเปิดตัว ได้แก่ ลดพื้นผิวการโจมตี ใช้สิทธิ์ขั้นต่ำที่จำเป็น (least privilege) แบ่งส่วนเครือข่าย และสมมติว่าส่วนประกอบจะถูกสำรวจ ในด้านสุขภาพและการดูแล เรื่องนี้แยกไม่ออกจากความปลอดภัยทางคลินิกและสารสนเทศกำกับ (หัวข้อ 1.6 — ความปลอดภัยทางคลินิกและการจัดการความเสี่ยง หัวข้อ 1.7 — ธรรมาภิบาลสารสนเทศ การคุ้มครองข้อมูล และความมั่นคงปลอดภัยไซเบอร์) เพราะการละเมิดเป็นทั้งอันตรายต่อข้อมูลและ เมื่อทำให้ระบบหยุด เป็นเหตุการณ์ด้านความปลอดภัยของผู้ป่วย ซอฟต์แวร์ที่ไม่ได้รับการสนับสนุนและอุดช่องโหว่ไม่ได้เป็นการตัดสินใจด้านความมั่นคงปลอดภัยที่คุณทำโดยปริยาย ดังนั้นจงตัดสินใจอย่างตั้งใจพร้อมมาตรการลดผลกระทบ หรือไม่ทำเลย

  9. ตัดสินใจสร้าง ซื้อ หรือตั้งค่าบนต้นทุนรวมของความเป็นเจ้าของ ไม่ใช่ราคาป้าย สำหรับแต่ละขีดความสามารถ เปรียบเทียบการสร้างเฉพาะ การซื้อผลิตภัณฑ์ และการตั้งค่าแพลตฟอร์มที่มีอยู่ ด้วยต้นทุนตลอดอายุเต็ม ได้แก่ การโฮสต์ ใบอนุญาต การบูรณาการ การสนับสนุน การอัปเกรด และการออกจากระบบในที่สุด ไม่ใช่ราคาแรก ให้ความสำคัญกับการซื้อหรือตั้งค่าสำหรับความต้องการทั่วไป และสงวนการสร้างไว้สำหรับความแตกต่างที่แท้จริง และชั่งน้ำหนักการผูกติดที่แต่ละทางเลือกสร้างขึ้น ทำเรื่องนี้ร่วมกับเพื่อนร่วมงานด้านพาณิชย์ (หัวข้อ 6.3 — การจัดซื้อจัดจ้างและพาณิชย์) เพราะเวลาที่ถูกที่สุดที่จะรับประกันส่วนต่อประสานเปิดและสิทธิ์ในการออกจากระบบคือก่อนลงนาม

  10. ถือว่ารายจ่ายคลาวด์เป็นวินัยร่วมระหว่างวิศวกรรมและการเงิน (FinOps) ให้ทีมมองเห็นชัดว่าบริการของตนมีต้นทุนเท่าใดด้วยการติดแท็กทรัพยากรคลาวด์ไปยังเจ้าของ ปรับขนาดอินสแตนซ์ให้พอดีกับการใช้งานจริง และปิดทรัพยากรที่ว่างหรือจัดสรรเกินแทนที่จะจ่ายทุกเดือน ทำให้ทีมที่ดำเนินบริการรับผิดชอบต่อต้นทุนการดำเนินงาน เพื่อให้ผู้ที่อยู่ในตำแหน่งที่ดีที่สุดที่จะลดความสิ้นเปลืองเป็นผู้ที่เห็นใบเรียกเก็บเงิน คลาวด์แบบจ่ายตามการใช้งานที่ไม่มีวินัยนี้กินงบประมาณที่ควรใช้ดูแลผู้ป่วยอย่างเงียบ ๆ และการเลื่อนไหลนั้นแทบไม่ถูกสังเกตจนกว่าใบแจ้งหนี้บังคับให้ตั้งคำถาม

  11. ออกแบบสถาปัตยกรรมโดยถือต้นทุนเป็นข้อกำหนดที่ไม่ใช่ฟังก์ชันชั้นหนึ่ง และชั่งน้ำหนักกับคาร์บอนและความยืดหยุ่น ถือต้นทุนเหมือนที่ถือสมรรถนะ ความมั่นคงปลอดภัย และความพร้อมใช้งาน คือคุณสมบัติที่ออกแบบอย่างตั้งใจ ประมาณการก่อนสร้าง และทบทวนเมื่อการใช้งานเติบโต ชั่งน้ำหนักอย่างชัดเจนกับคาร์บอน (ดูหัวข้อ 8.5 — ความยั่งยืนและเน็ตซีโร) และความยืดหยุ่น เพราะทั้งสามมักเคลื่อนไปด้วยกัน แต่อย่าไล่ตามใบเรียกเก็บเงินต่ำสุดโดยแลกกับความปลอดภัย ความสามารถในการกู้คืน หรือผลลัพธ์ของผู้ป่วย คำตอบที่ถูกต้องคือต้นทุนต่ำที่สุดที่ยังบรรลุพันธะด้านความปลอดภัยทางคลินิกและความยืดหยุ่นของคุณ ไม่ใช่ทางเลือกที่ถูกที่สุดเมื่อมองแยกเดี่ยว

คำถามสำหรับหารือกับทีมของคุณ#

  1. ระบบสำคัญใดของเราที่ไม่ได้รับการสนับสนุนหรืออุดช่องโหว่ไม่ได้ในปัจจุบัน และความเสี่ยงที่แท้จริงของเราคืออะไรหากระบบหนึ่งถูกโจมตีหรือล้มเหลว เริ่มจากระบบที่บริการทางคลินิกและการปฏิบัติการขาดไม่ได้จริง ๆ และระบุอย่างเป็นรูปธรรมว่าระบบใดใช้ซอฟต์แวร์ที่ไม่ได้รับการอัปเดตความมั่นคงปลอดภัยหรือการสนับสนุนจากผู้ขายอีกต่อไป ถามว่าจะเกิดอะไรขึ้นกับผู้ป่วย บุคลากร และข้อมูล หากแต่ละระบบถูกแรนซัมแวร์โจมตีหรือหยุดไปเฉย ๆ และการกู้คืนใช้เวลานานเท่าใด แยกระบบที่คุณยอมรับความเสี่ยงโดยรู้ตัวพร้อมมาตรการลดผลกระทบ ออกจากระบบที่ไม่มีใครประเมินความเปราะบาง พิจารณาว่าความเสี่ยงนี้ปรากฏในทะเบียนความเสี่ยงขององค์กรหรือฝังอยู่ในสเปรดชีตที่คณะกรรมการไม่เคยเห็น ย้อนดู WannaCry ความเสียหายไม่ได้มาจากความซับซ้อน แต่มาจากหนี้ที่รู้อยู่และไม่ได้แก้ในระบบสำคัญ หากคุณตอบเรื่องนี้ด้วยหลักฐานไม่ได้ ช่องว่างนั้นเองคือข้อค้นพบเร่งด่วนที่สุดของคุณ เพราะคุณไม่อาจสนับสนุนงบประมาณให้ความเสี่ยงที่คุณยังไม่ได้ตั้งชื่อ

  2. เราถูกผูกติดที่ไหน และการออกจากแพลตฟอร์มที่ใหญ่ที่สุดของเราจะมีต้นทุนจริงเท่าใด หลายองค์กรค้นพบราคาจริงของระบบปิดเมื่อพยายามเปลี่ยนมันเท่านั้น ไล่ดูว่าการย้ายออกจากแพลตฟอร์มคลินิกหรือองค์กรที่ใหญ่ที่สุดของคุณต้องใช้อะไรจริง ๆ คุณดึงข้อมูลออกมาในรูปแบบมาตรฐานที่ใช้ได้หรือไม่ ต้องรื้อส่วนต่อประสานที่เป็นกรรมสิทธิ์อะไรบ้าง และสัญญาระบุอะไรเรื่องความเป็นเจ้าของและการออกจากระบบ พิจารณาว่า "คลาวด์" กลายเป็นการผูกติดอีกแบบอย่างเงียบ ๆ หรือไม่ โดยข้อมูลและเครื่องมือพัวพันกับผู้ให้บริการรายเดียวจนการออกไม่เป็นทางปฏิบัติ ชั่งน้ำหนักกับความเปิดของทางเลือกและแพลตฟอร์มระดับชาติใด ๆ ที่คุณนำกลับมาใช้แทนได้ นี่ไม่ใช่ข้อโต้แย้งให้เปลี่ยนผู้จัดหาบ่อย ๆ แต่เป็นเรื่องการเข้าใจอำนาจต่อรองของคุณก่อนการเจรจาครั้งหน้า และไม่ปล่อยให้แผนที่นำทางของผู้ขายรายหนึ่งกลายเป็นทางเลือกเดียวของคุณอย่างเงียบ ๆ

  3. เราลงทุนเพียงพอหรือไม่ในการบำรุงรักษาและปรับสิ่งที่มีอยู่ให้สมเหตุสมผล หรือเฉพาะสิ่งใหม่และมองเห็นได้ ระบบใหม่ดึงดูดงบประมาณและความสนใจ ส่วนงานที่ไม่หรูหราอย่างการอุดช่องโหว่ การอัปเกรด การรวม และการปลดระวางอย่างปลอดภัยแทบไม่ได้ ซึ่งเป็นวิธีที่หนี้สะสมพอดี ถามว่างบประมาณดิจิทัลสัดส่วนเท่าใดที่ใช้รักษาระบบที่มีอยู่ให้ปลอดภัยและทันสมัยเมื่อเทียบกับการสร้างสิ่งใหม่ และมีใครเป็นเจ้าของสมดุลนั้นอย่างตั้งใจหรือไม่ หารือว่าการปลดระวางเคยได้รับทรัพยากรอย่างเหมาะสมหรือไม่ หรือระบบเก่าค้างอยู่เพียงเพราะการปิดมันไม่ใช่หน้าที่ของใคร พิจารณาแอปพลิเคชันซ้ำซ้อนที่ทำสิ่งเดียวกันข้ามองค์กร และต้องใช้อะไรเพื่อรวมมัน คิดว่าใครในระดับคณะกรรมการที่รับผิดชอบต่อสุขภาพของระบบโดยรวมแทนที่จะเป็นโครงการเฉพาะ องค์กรที่ให้งบเฉพาะสิ่งใหม่กำลังกู้ยืมจากความปลอดภัยในอนาคตของตนเอง และการชำระคืนมาถึงในเวลาที่เลวร้ายที่สุดเสมอ

  4. เรารู้จริงหรือไม่ว่าคลาวด์ของเรามีต้นทุนเท่าใด ใครเป็นเจ้าของใบเรียกเก็บเงินนั้น และรายจ่ายอยู่ภายใต้การควบคุมหรือไม่ คลาวด์แบบจ่ายตามการใช้งานอาจกินงบประมาณที่ควรใช้ดูแลผู้ป่วยอย่างเงียบ ๆ และการเลื่อนไหลแทบไม่ถูกสังเกตจนกว่าใบแจ้งหนี้บังคับให้ตั้งคำถาม ถามว่าทรัพยากรคลาวด์ถูกติดแท็กไปยังทีมและบริการที่เป็นเจ้าของหรือไม่ มีใครปรับขนาดอินสแตนซ์ตามการใช้งานจริงหรือไม่ และทรัพยากรที่ว่างหรือจัดสรรเกินเคยถูกปิดหรือไม่ หารือว่าผู้ที่ดำเนินบริการเห็นและตอบเรื่องต้นทุนการดำเนินงานของมันหรือไม่ หรือรายจ่ายคลาวด์ตกเป็นบรรทัดเดียวที่อธิบายไม่ได้ในงบประมาณกลางที่ไม่มีใครแยกย่อยได้ พิจารณาว่าต้นทุนถูกถือเป็นข้อกำหนดที่ไม่ใช่ฟังก์ชันชั้นหนึ่ง คือประมาณการก่อนสร้างและทบทวนเมื่อการใช้งานเติบโต หรือเพิ่งค้นพบภายหลังเกิดเหตุ ตรงไปตรงมาเรื่องความตึงเครียดระหว่างอิสระด้านวิศวกรรมกับการควบคุมทางการเงิน และเรื่องการชั่งน้ำหนักต้นทุนกับคาร์บอนและความยืดหยุ่นแทนที่จะไล่ตามใบเรียกเก็บเงินต่ำสุด คำตอบที่ตรงไปตรงมาระบุผู้ถือวินัย FinOps และแสดงหลักฐานว่ามันได้ผล แทนที่จะสันนิษฐานว่าคลาวด์ถูกกว่าเพราะทันสมัย

  5. เมื่อเราต้องการขีดความสามารถใหม่ เราตัดสินใจอย่างไรระหว่างสร้าง ซื้อ และตั้งค่าสิ่งที่เรามีอยู่ และบนฐานใด สัญชาตญาณที่จะสร้างเฉพาะ หรือซื้อผลิตภัณฑ์ที่สาธิตได้ดีที่สุด มักชนะก่อนที่ใครจะเปรียบเทียบต้นทุนตลอดอายุเต็ม ไล่ดูว่าทางเลือกสำคัญไม่กี่ครั้งล่าสุดของคุณถูกตัดสินจริงอย่างไร ชั่งน้ำหนักการโฮสต์ ใบอนุญาต การบูรณาการ การสนับสนุน การอัปเกรด และการออกจากระบบในที่สุด หรือเพียงราคาแรก ถามว่าคุณสงวนการสร้างไว้สำหรับความแตกต่างที่แท้จริงและตั้งต้นที่การซื้อหรือตั้งค่าสำหรับความต้องการทั่วไป หรือการสร้างเฉพาะแพร่หลายอย่างเงียบ ๆ เพราะทีมชอบ พิจารณาว่าใครอยู่ในห้องสำหรับการตัดสินใจเหล่านี้ ทั้งเพื่อนร่วมงานด้านพาณิชย์และคลินิกนอกเหนือจากวิศวกร และการผูกติดที่แต่ละทางเลือกสร้างถูกประเมินก่อนลงนามแทนที่จะค้นพบภายหลัง ทบทวนว่าหลักการสถาปัตยกรรมของคุณ ("นำกลับมาใช้ก่อนซื้อ ซื้อก่อนสร้าง") ผูกมัดทางเลือกเหล่านี้จริงหรือถูกเพิกเฉยอย่างเงียบ ๆ คำตอบที่ตรงไปตรงมาชี้ไปที่การตัดสินใจจริงที่ต้นทุนรวมของความเป็นเจ้าของ ไม่ใช่ราคาป้าย เปลี่ยนผลลัพธ์

  6. เรามีขีดความสามารถด้านสถาปัตยกรรมภายในองค์กรเพื่อกำกับการตัดสินใจของเราเองหรือไม่ หรือเราพึ่งพาผู้จัดหาที่เราควรทำให้รับผิดชอบ สถาปัตยกรรมคือที่ที่ภาระผูกพันที่ใหญ่และยาวนานที่สุดถูกทำขึ้น แต่หลายองค์กรกลวงขีดความสามารถที่จำเป็นต่อการตัดสินใจให้ดี โดยพึ่งพาผู้ขายที่ผลิตภัณฑ์กำลังถูกประเมินให้บอกว่าอะไรคือสิ่งที่ดี ถามว่าคุณมีทักษะสถาปัตยกรรมองค์กรและโซลูชันที่น่าเชื่อถือฝั่งตนเองหรือไม่ และคณะกำกับการออกแบบของคุณมีบุคลากรเพื่อเอื้ออำนวยทีมหรือเพียงประทับตรา หารือว่าการตัดสินใจสำคัญที่ย้อนกลับยากถูกทดสอบกับหลักการที่ตกลงกันจริงหรือถูกมอบหมายโดยปริยายให้ผู้จัดหารายที่ใกล้ปัญหาที่สุด พิจารณาว่าคุณจะรู้จักข้อเสนอแนะด้านสถาปัตยกรรมที่แย่ได้อย่างไรหากไม่มีความเชี่ยวชาญอิสระมาท้าทาย ชั่งน้ำหนักต้นทุนของการสร้างและรักษาขีดความสามารถนี้กับต้นทุนที่ใหญ่กว่ามากของการผูกติดและงานซ้ำที่การไม่มีมันก่อให้เกิด คำตอบที่ตรงไปตรงมาแยกการตัดสินใจที่คุณเป็นเจ้าของได้จริงออกจากสิ่งที่คุณกำลังรับไว้ด้วยความไว้วางใจ

ในทางปฏิบัติ: ตัวอย่างด้านสุขภาพและการดูแล#

ระบบเทคนิคของ acute hospital trust แห่งหนึ่งเติบโตตามธรรมชาติมาสองทศวรรษ ที่ศูนย์กลางคือระบบบริหารผู้ป่วยที่ทำงานบนระบบปฏิบัติการซึ่งผู้ขายเลิกสนับสนุนไปเมื่อสิบแปดเดือนก่อน รอบ ๆ มีแอปพลิเคชันมากกว่าสองร้อยตัว หลายตัวซื้อโดยแผนก บางตัวทำงานซ้ำซ้อนกัน และไม่มีใครถือรายการครบถ้วน เหตุการณ์เฉียดฉิว คือความพยายามโจมตีด้วยแรนซัมแวร์ที่ถูกสกัดได้เพราะโชคมากกว่าการออกแบบ ทำให้คณะกรรมการถามคำถามที่ไม่เคยถามมาก่อนว่า เรากำลังใช้อะไรอยู่กันแน่ และเปราะบางเพียงใด

หัวหน้าเจ้าหน้าที่สารสนเทศดิจิทัลต้านทานสัญชาตญาณที่จะเปิดโครงการ "แทนที่ทุกอย่าง" ครั้งใหญ่ครั้งเดียว และทำงานน่าเบื่อก่อน trust สร้างพอร์ตโฟลิโอแอปพลิเคชันที่เป็นปัจจุบัน ได้แก่ ทุกระบบ เจ้าของทางธุรกิจ ความสามารถในการสนับสนุน ต้นทุน และความเสี่ยง ภาพที่ได้น่าตกใจ คือหนึ่งในห้าของแอปพลิเคชันอยู่บนซอฟต์แวร์ที่ไม่ได้รับการสนับสนุน และสิบกว่าตัวทำซ้ำขีดความสามารถที่มีอยู่แล้วที่อื่น แต่เป็นครั้งแรกที่มองเห็นได้ และความเสี่ยงที่เลวร้ายที่สุดถูกนำขึ้นทะเบียนความเสี่ยงขององค์กรทันทีที่คณะกรรมการเห็นได้

จากบัญชีรายการนั้น trust ตัดสินใจอย่างตั้งใจโดยอาศัยหลักการสถาปัตยกรรมที่ตกลงไว้ไม่กี่ข้อ ระบบบริหารผู้ป่วยที่ไม่ได้รับการสนับสนุนถูกจัดลำดับให้แทนที่ จัดซื้อเป็นผลิตภัณฑ์ตั้งค่าได้พร้อมสิทธิ์ตามสัญญาเรื่อง API เปิดและการดึงข้อมูล เพื่อไม่ให้ trust ถูกผูกติดอีก ภาระงานที่เหมาะสมย้ายไปคลาวด์สาธารณะ โดยประเมินทีละตัวแทนที่จะตามสโลแกน พร้อมชั่งน้ำหนักคาร์บอนและความย้ายได้ควบคู่ต้นทุน คณะกำกับการออกแบบขนาดเล็กทบทวนการตัดสินใจสำคัญและอนุมัติเรื่องประจำอย่างรวดเร็ว แอปพลิเคชันแผนกที่ซ้ำซ้อนสิบสองตัวถูกรวมเหลือสามตัว และระบบที่ปลดระวางถูกปิดอย่างถูกต้อง คือย้ายข้อมูลภายใต้กฎการเก็บรักษาที่ชัดเจน ตรวจสอบการพึ่งพา แจ้งผู้ใช้ และจึงปิด

ไม่มีสิ่งใดเหล่านี้เป็นข่าวพาดหัว แต่สิบแปดเดือนต่อมา trust รู้ว่าตนใช้อะไร หนี้ที่อันตรายที่สุดกำลังถูกชำระตามแผนที่มีงบประมาณแทนที่จะหวังว่าจะหายไป และการบูรณาการบันทึกการดูแลร่วมใหม่ถูกส่งมอบภายในไม่กี่สัปดาห์เพราะระบบทดแทนเปิด API เปิด เหตุการณ์เฉียดฉิวกลายเป็นช่วงเวลาที่ trust เริ่มบริหารสถาปัตยกรรมของตนแทนที่จะถูกมันบริหาร

มุมมองตามภาคส่วน#

สตาร์ทอัป#

สตาร์ทอัปด้านสุขภาพดิจิทัลมีความได้เปรียบที่แทบไม่มีระบบเดิม และควรปกป้องสิ่งนั้นอย่างเข้มงวด สร้างแบบคลาวด์เนทีฟตั้งแต่ต้น เปิด API เปิด และถือว่าปลอดภัยโดยการออกแบบเป็นฟีเจอร์หลักแทนที่จะเป็นต้นทุนภายหลัง เพราะผู้ซื้อ NHS ที่ระมัดระวังจะตรวจสอบสถาปัตยกรรมความมั่นคงปลอดภัยและเงื่อนไขการดึงข้อมูลของคุณอย่างใกล้ชิด รักษาแพลตฟอร์มบางที่สุดที่ใช้งานได้ของคุณให้บางจริง ต้านทานความอยากออกแบบเกินสำหรับขนาดที่คุณยังไม่มี เส้นทางที่เร็วที่สุดสู่การสะสมหนี้ทางเทคนิคที่เป็นอัมพาตคือส่งโค้ดที่ทำเพื่อความสะดวกภายใต้แรงกดดันของนักลงทุนและไม่เคยชำระคืน ดังนั้นจงตัดสินใจอย่างตั้งใจและมองเห็นได้ว่าจะรับหนี้ใด อย่างขัดแย้ง การออกแบบให้ลูกค้าดึงข้อมูลออกและจากไปได้คือสิ่งที่สร้างความไว้วางใจที่ทำให้พวกเขาอยู่ต่อ

ธุรกิจขนาดเล็ก#

ผู้ให้บริการรายเล็กที่ก่อตั้งมานาน เช่น คลินิกแพทย์ทั่วไป (GP practice) ร้านขายยาชุมชน สถานดูแลผู้สูงอายุ คลินิกแห่งเดียว หรือผู้จัดหาเทคโนโลยีสุขภาพขนาดเล็กที่พ้นช่วงสตาร์ทอัป มีหน้าที่เท่ากับ trust ขนาดใหญ่แต่มีทรัพยากรเพียงเสี้ยวเดียวและแทบไม่มีขีดความสามารถด้านไอทีโดยเฉพาะ ในที่นี้สถาปัตยกรรมส่วนใหญ่คือวินัยของการซื้อให้ดี ให้ความสำคัญกับซอฟต์แวร์เป็นบริการ (SaaS) ที่มีชื่อเสียง เพื่อให้ผู้จัดหาแบกรับการโฮสต์ การอุดช่องโหว่ และความมั่นคงปลอดภัยที่คุณจัดบุคลากรเองไม่ไหว และอ่านสัญญาเรื่องสิทธิ์การดึงข้อมูลและการออกจากระบบก่อนลงนาม เพราะการผูกติดกัดแรงที่สุดเมื่อคุณไม่มีอำนาจต่อรอง เก็บบัญชีรายการง่าย ๆ ของระบบไม่กี่ตัวที่คุณพึ่งพาและรู้ว่าตัวใดยังได้รับการสนับสนุน เพราะแม้ระบบเล็กก็ซ่อนเครื่องที่ไม่ได้อุดช่องโหว่ซึ่งทำให้คลินิกหยุดได้ ยืนยันให้ผู้จัดหาเป็นไปตามมาตรฐานที่ยอมรับ เช่น Data Security and Protection Toolkit แทนที่จะพยายามประเมินความมั่นคงปลอดภัยตั้งแต่ศูนย์ เมื่อเงินตึงตัวมีสิ่งล่อใจให้คงระบบเก่าที่ไม่ได้รับการสนับสนุนไว้เพื่อหลีกเลี่ยงค่าใช้จ่าย แต่นั่นเป็นการตัดสินใจด้านความปลอดภัยที่คุณควรทำอย่างตั้งใจ ไม่ใช่ปล่อยให้เลื่อนไหล

องค์กรขนาดใหญ่#

trust หรือผู้จัดหาขนาดใหญ่แบกรับระบบที่สะสมมาหลายทศวรรษและเริ่มใหม่ตั้งแต่ต้นไม่ได้ ยุทธศาสตร์ที่เป็นจริงคือวิวัฒนาการอย่างมีวินัย ได้แก่ ดูแลพอร์ตโฟลิโอที่เป็นปัจจุบัน วางชั้นแบบเปิดที่อิงตาม API หน้าสิ่งที่ต้องคงอยู่ และชำระหนี้ที่อันตรายที่สุดตามแผนที่มีงบประมาณและจัดลำดับความสำคัญ แทนที่จะเป็นการตื่นตระหนกเป็นครั้งคราว ดำเนินคณะกำกับการออกแบบที่ได้รับความเคารพเพราะเอื้อต่อการส่งมอบ ไม่ใช่ถูกกลัวเพราะขัดขวาง และทำให้หนี้ทางเทคนิคเป็นความเสี่ยงถาวรระดับคณะกรรมการที่มีเจ้าของที่มีชื่อ ป้องกันการผูกติดทุกครั้งที่ต่อสัญญา และถือว่าการปลดระวางเป็นงานจริงที่มีทรัพยากร ไม่ใช่เรื่องที่นึกถึงทีหลัง นี่คือวินัยการนำกลับมาใช้และส่วนต่อประสานเปิดเดียวกับที่กำกับแพลตฟอร์มปฏิบัติการหลักในหัวข้อ 5.4 — การวางแผนทรัพยากรองค์กร (ERP)

ภาครัฐ#

หน่วยงานระดับชาติและภูมิภาคกำหนดเงื่อนไขที่ทั้งภาคส่วนดำเนินงาน และทางเลือกด้านสถาปัตยกรรมของพวกเขาส่งผลกระเพื่อมออกไป สิ่งที่มีค่าที่สุดที่ภาครัฐทำได้คือบังคับมาตรฐานเปิด จัดหาแพลตฟอร์มระดับชาติที่นำกลับมาใช้ได้เพื่อให้องค์กรท้องถิ่นสร้างครั้งเดียว และกำหนดความคาดหวังด้านคลาวด์ ความมั่นคงปลอดภัย และความยั่งยืนที่ยกระดับพื้นฐานทุกที่ ที่สำคัญคือ ภาครัฐต้องสนับสนุนงบประมาณงานระดับชาติที่ไม่หรูหรา ได้แก่ การแก้ไขระบบเดิม การดูแลศัพท์มาตรฐาน การสนับสนุนการปลดระวาง ซึ่งไม่มีองค์กรใดจะออกเงินเองลำพังแต่ทุกคนพึ่งพา มาตรฐานที่ดีพอซึ่งบังคับใช้อย่างเข้มงวดและนำกลับมาใช้อย่างกว้างขวางดีกว่ามาตรฐานที่เหนือกว่าในทางทฤษฎีแต่นำไปใช้ไม่สม่ำเสมอ บทบาทการดูแลนี้เชื่อมโยงกับหัวข้อ 9.1 — การทำงานร่วมกับรัฐบาลท้องถิ่นและระดับชาติ และกับวิธีที่พันธมิตรร่วมมือกันในหัวข้อ 9.0 — การทำงานร่วมกับองค์กรพันธมิตร

รูปแบบความล้มเหลวที่พบบ่อย#

  • ระบบที่มองไม่เห็น ใช้แอปพลิเคชันหลายร้อยตัวโดยไม่มีบัญชีรายการที่ถูกต้อง ทำให้ไม่รู้ความเสี่ยง ไม่สังเกตความซ้ำซ้อน และสัญญาณแรกของความเปราะบางคือเหตุขัดข้องหรือการละเมิด
  • หนี้ที่ซ่อนจากคณะกรรมการ เก็บซอฟต์แวร์ที่ไม่ได้รับการสนับสนุนและหนี้ทางเทคนิคเป็นเชิงอรรถทางเทคนิคแทนที่จะเป็นความเสี่ยงขององค์กรที่มีชื่อ จึงไม่มีงบประมาณจนกว่าจะล้มเหลว
  • คลาวด์เป็นสโลแกน ยกระบบเดิมที่ไม่เปลี่ยนแปลงไปคลาวด์สาธารณะตามหลักการ ย้ายปัญหาไปด้วยต้นทุนที่สูงกว่า หรือพัวพันข้อมูลและเครื่องมือกับผู้ให้บริการรายเดียวลึกจนกลายเป็นการผูกติดแบบใหม่
  • คณะกำกับการออกแบบเป็นคอขวด ปล่อยให้การกำกับดูแลสถาปัตยกรรมกลายเป็นด่านช้าที่ทีมเลี่ยง ทำให้เกิดสถาปัตยกรรมเงาที่ไม่มีเอกสารซึ่งแย่กว่าไม่มีเลย
  • สร้างทั้งที่ควรตั้งค่า เลือกสร้างเฉพาะสำหรับความต้องการทั่วไปโดยอิงราคาป้ายแทนต้นทุนรวมของความเป็นเจ้าของ และรับมรดกการบำรุงรักษาหนึ่งทศวรรษที่ไม่ได้ตั้งงบไว้
  • ไม่เคยปลดระวาง ปล่อยระบบล้าสมัยทำงาน "เผื่อไว้" ซึ่งแต่ละระบบเป็นพื้นผิวการโจมตี ต้นทุนใบอนุญาต และภาระการบำรุงรักษาที่ไม่มีใครเป็นเจ้าของ
  • ความมั่นคงปลอดภัยที่เติมทีหลัง ถือว่าความมั่นคงปลอดภัยเป็นด่านก่อนเปิดตัวแทนที่จะเป็นปัจจัยนำเข้าด้านการออกแบบ พื้นผิวการโจมตีจึงถูกกำหนดไว้นานก่อนที่ใครจะประเมิน
  • การผูกติดโดยปริยาย ลงนามแพลตฟอร์มที่ไม่มีส่วนต่อประสานเปิดหรือสิทธิ์การดึงข้อมูล และค้นพบต้นทุนของกับดักเมื่อพยายามออกเท่านั้น

แบบจำลองระดับวุฒิภาวะ#

มิติ เริ่มต้น พัฒนา ทำให้เป็นมาตรฐาน บริหารจัดการ ประสานบูรณาการ
การมองเห็นระบบ ไม่มีบัญชีรายการที่เชื่อถือได้ ไม่รู้ความเสี่ยง รายการบางส่วนเก็บแยกส่วน พอร์ตโฟลิโอที่เป็นปัจจุบันพร้อมเจ้าของ ต้นทุน ความเสี่ยงต่อแอปพลิเคชัน ติดตามตัวชี้วัดพอร์ตโฟลิโอและทบทวนเทียบกับเป้าหมาย แก้ช่องว่างอย่างจริงจัง พอร์ตโฟลิโอที่ดูแลต่อเนื่องขับเคลื่อนการตัดสินใจลงทุน
หนี้ทางเทคนิคและระบบเดิม ไม่ได้บริหาร ไม่สังเกตระบบที่ไม่ได้รับการสนับสนุน รู้โดยไม่เป็นทางการแต่ไม่อยู่ในทะเบียนความเสี่ยง อยู่ในทะเบียนความเสี่ยงขององค์กรพร้อมแผนแก้ไขที่มีงบประมาณ วัดปริมาณหนี้และลดตามเป้าหมายที่วัดได้ พร้อมมาตรการควบคุมที่ได้รับการรับรอง ชำระหนี้อย่างจริงจัง วางแผนการสิ้นอายุก่อนมาถึง
คลาวด์และการโฮสต์ เฉพาะกิจ ใช้ในองค์กรเป็นค่าเริ่มต้น ใช้คลาวด์บางส่วน เลือกเป็นกรณี ๆ ยุทธศาสตร์ทีละภาระงานที่ตั้งใจ ชั่งน้ำหนักคาร์บอน วัดต้นทุน คาร์บอน และความยืดหยุ่นต่อบริการและบริหารตามเป้าหมาย (FinOps) ย้ายได้ ปรับให้เหมาะสม บริหารความยั่งยืนและต้นทุนอย่างจริงจัง
การกำกับดูแลสถาปัตยกรรม ไม่มี ทุกโครงการตัดสินใจเอง ทบทวนไม่เป็นทางการโดยบุคคล คณะกำกับการออกแบบพร้อมหลักการชัดเจนและช่องทางเร็ว วัดการตัดสินใจเทียบกับหลักการ รับรองการยึดตามและผลลัพธ์ การกำกับดูแลที่เอื้ออำนวย ทีมใช้หลักการด้วยตนเอง
ส่วนต่อประสานและการผูกติด เป็นกรรมสิทธิ์ ฮาร์ดไวร์ ไม่มีสิทธิ์ออกจากระบบ มี API บางส่วน บังคับมาตรฐานอย่างอ่อน กำหนดให้มี API เปิดและสิทธิ์การดึงข้อมูล วัดและรับรองการใช้ API และสิทธิ์ออกจากระบบทั่วทั้งระบบ เชื่อมโยงอย่างหลวม อิงมาตรฐาน เปลี่ยนผู้จัดหาแทนกันได้จริง

รายการตรวจสอบ#

  • พอร์ตโฟลิโอแอปพลิเคชันที่เป็นปัจจุบันบันทึกเจ้าของ ต้นทุน ความสามารถในการสนับสนุน และความเสี่ยงของทุกระบบ และทบทวนสม่ำเสมอ
  • ระบบสำคัญที่ไม่ได้รับการสนับสนุนและอุดช่องโหว่ไม่ได้ถูกระบุและอยู่ในทะเบียนความเสี่ยงขององค์กร ไม่ใช่ในสเปรดชีตทางเทคนิค
  • ชุดหลักการสถาปัตยกรรมสั้น ๆ ที่ตกลงกันไว้ถูกใช้จริงเพื่อตัดสินและให้เหตุผลการตัดสินใจ
  • คณะกำกับการออกแบบทบทวนการตัดสินใจสำคัญที่ย้อนกลับยาก และอนุมัติเรื่องประจำอย่างรวดเร็ว เอื้ออำนวยมากกว่าขัดขวาง
  • การนำคลาวด์มาใช้ถูกประเมินทีละภาระงาน โดยชั่งน้ำหนักที่ตั้งของข้อมูล ความยืดหยุ่น ต้นทุน ความย้ายได้ และคาร์บอน
  • หนี้ทางเทคนิคมีเจ้าของที่มีชื่อและแผนแก้ไขที่มีงบประมาณ ไม่ใช่เพียงการดับไฟเป็นครั้งคราว
  • ระบบที่ซ้ำซ้อนและล้าสมัยถูกปรับให้สมเหตุสมผล และการปลดระวางมีทรัพยากรสำหรับการย้ายข้อมูล การเก็บรักษา และการตรวจสอบการพึ่งพา
  • ขีดความสามารถใหม่เปิด API ที่เปิดและมีเวอร์ชัน เพื่อให้เปลี่ยนส่วนประกอบได้โดยไม่ต้องสร้างรอบข้างใหม่
  • ความมั่นคงปลอดภัยถูกออกแบบไว้ตั้งแต่ต้น ได้แก่ พื้นผิวการโจมตีน้อยที่สุด สิทธิ์ขั้นต่ำที่จำเป็น การแบ่งส่วน ไม่ใช่เติมก่อนเปิดตัว
  • การตัดสินใจสร้าง/ซื้อ/ตั้งค่าทำบนต้นทุนรวมของความเป็นเจ้าของและการผูกติด โดยรับประกันสิทธิ์ออกจากระบบและการดึงข้อมูลก่อนลงนาม
