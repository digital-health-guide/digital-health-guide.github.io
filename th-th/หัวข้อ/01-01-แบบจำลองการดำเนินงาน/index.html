หัวข้อ 1.1 — แบบจำลองการดำเนินงาน

สรุปในหนึ่งประโยค: แบบจำลองการดำเนินงานเป้าหมาย (target operating model: TOM) คือการออกแบบอย่างตั้งใจว่ากลยุทธ์ขององค์กรไหลผ่านสายธารคุณค่า ขีดความสามารถ ทีม การกำกับดูแล เทคโนโลยี ข้อมูล และผู้จัดหาสินค้าและบริการอย่างไร เพื่อส่งมอบผลลัพธ์ด้านสุขภาพและการดูแลดิจิทัล และการวางรูปแบบให้ถูกต้องเป็นตัวกำหนดว่าทุกสิ่งที่ตามมาจะรวดเร็วและปลอดภัย หรือช้าและเปราะบาง

ทำไมเรื่องนี้จึงสำคัญในด้านสุขภาพและการดูแล#

องค์กรสุขภาพดิจิทัลส่วนใหญ่ไม่ได้ล้มเหลวเพราะขาดคนเก่งหรือเทคโนโลยี แต่ล้มเหลวเพราะแบบจำลองการดำเนินงานของตนสู้กับตัวเอง เงินทุนผูกกับโครงการที่มีกำหนดเวลา สิทธิ์ในการตัดสินใจคลุมเครือ และทุกทีมสร้างระบบล็อกอิน การเชื่อมต่อ และการตรวจสอบย้อนหลังแบบเดียวกันซ้ำแล้วซ้ำอีก ผลที่ได้คือต้นทุนซ้ำซ้อนจากเงินสาธารณะ ความปลอดภัยทางคลินิกที่ไม่สม่ำเสมอ และบริการที่แบ่งปันข้อมูลข้ามระบบการดูแลแบบบูรณาการ (ICS) ไม่ได้

แบบจำลองการดำเนินงานในโดเมนนี้มีลักษณะเฉพาะ เพราะต้องประสานสิ่งดีที่ขัดแย้งกัน แบบจำลองต้องเป็นสหพันธ์พอที่จะเคารพความเป็นอิสระขององค์กรที่มีอธิปไตยของตน ไม่ว่าจะเป็นโรงพยาบาล องค์กรปกครองส่วนท้องถิ่น หรือคลินิก GP แต่ก็ต้องสอดคล้องพอที่จะให้ผู้ป่วยได้ประสบการณ์ที่ปลอดภัยเดียวกันข้ามองค์กรเหล่านั้น ต้องสมดุลระหว่าง run (รักษาให้ระบบทางคลินิกพร้อมใช้งานอย่างปลอดภัย) กับ change (ปรับปรุงระบบ) ในเมื่อระบบหยุดทำงานอาจส่งผลต่อการดูแล และต้องใช้จ่ายอย่างเหมาะสม คือการประกันคุณภาพที่หนักพอสำหรับความรับผิดชอบต่อสาธารณะและความปลอดภัยทางคลินิก แต่เบาพอที่จะไม่บีบคอการทำซ้ำเป็นรอบ TOM คือที่ที่ข้อแลกเปลี่ยนเหล่านี้ถูกทำให้ชัดเจน แทนที่จะปล่อยให้เป็นไปตามบังเอิญ

แนวคิดหลัก#

ชั้นต่าง ๆ ของแบบจำลองการดำเนินงาน TOM ที่ใช้ได้จริงเป็นชั้นซ้อนกัน แต่ละชั้นรับใช้ชั้นที่อยู่เหนือขึ้นไป

  • กลยุทธ์และผลลัพธ์ — ผลลัพธ์ที่วัดได้ของประชากรและบริการที่คุณมีอยู่เพื่อปรับปรุง (มักแสดงเป็น OKR ดู หัวข้อ 1.3 — การตัดสินใจที่ขับเคลื่อนด้วยหลักฐาน)
  • สายธารคุณค่า (value stream) — กระแสงานตั้งแต่ต้นจนจบที่ส่งมอบคุณค่าให้ผู้ใช้ เช่น "ส่งต่อ คัดกรอง และรักษาผู้ป่วย" จัดรอบเส้นทางของประชาชน ไม่ใช่ผังองค์กร
  • ขีดความสามารถ — สิ่งที่คุณต้องทำได้ (การยืนยันตัวตน การจองนัดหมาย การบันทึกทางคลินิก การวิเคราะห์) ขีดความสามารถคงที่แม้วิธีแก้จะเปลี่ยน
  • ทีม — ผู้คนที่จัดระเบียบเพื่อส่งมอบขีดความสามารถและสายธารคุณค่า (ดู Team Topologies ด้านล่าง)
  • การกำกับดูแลและสิทธิ์ในการตัดสินใจ — ใครตัดสินใจอะไร และใช้การประกันคุณภาพอย่างไร
  • เทคโนโลยีและข้อมูล — แพลตฟอร์ม มาตรฐาน และสถาปัตยกรรมข้อมูลที่ทีมสร้างบนนั้น
  • ผู้จัดหาสินค้าและบริการ — ตลาดที่คุณซื้อและวิธีบริหารตลาดนั้น

การออกแบบจากบนลงล่าง (กลยุทธ์ → สายธารคุณค่า → ขีดความสามารถ) ทำให้ทีมและเทคโนโลยีสอดคล้องกับผลลัพธ์ แทนที่จะสอดคล้องกับโครงสร้างเดิม

แบบรวมศูนย์ เทียบกับแบบสหพันธ์ เทียบกับแบบแพลตฟอร์ม แบบจำลองรวมศูนย์กระจุกการส่งมอบไว้ที่ทีมเดียวหรือหน่วยงานที่แยกออกมา ทำให้สม่ำเสมอและมาตรฐานเดียวได้ในราคาถูก แต่เป็นคอขวดและมักห่างจากความต้องการในท้องถิ่น แบบจำลองสหพันธ์มอบการส่งมอบให้โรงพยาบาลและพื้นที่ ตอบสนองได้ดีและเป็นเจ้าของในท้องถิ่น แต่มีแนวโน้มซ้ำซ้อนและแตกต่างกัน แบบจำลองแพลตฟอร์มคือรูปแบบที่ประสานทั้งสอง คือทีมกลางจัดให้มีขีดความสามารถที่ใช้ร่วมและนำกลับมาใช้ซ้ำได้ (การยืนยันตัวตน การทำงานร่วมกันได้ การโฮสต์ ระบบออกแบบ) เป็นแพลตฟอร์ม และทีมแบบสหพันธ์สร้างต่อยอดได้อย่างรวดเร็ว ระบบสุขภาพที่เติบโตเต็มที่ส่วนใหญ่บรรจบที่ "แพลตฟอร์มบวกสหพันธ์"

Team Topologies กรอบแนวคิดนี้ระบุประเภททีมสี่แบบ ได้แก่ ทีมที่จัดตามสายธารงาน (stream-aligned: เป็นเจ้าของสายธารคุณค่า) ทีมแพลตฟอร์ม (platform: ให้ขีดความสามารถแบบบริการตนเอง) ทีมเสริมพลัง (enabling: ฝึกสอนผู้อื่นให้พัฒนาขีดความสามารถ) และทีมระบบย่อยซับซ้อน (complicated-subsystem: งานเฉพาะทางเชิงลึก เช่น อัลกอริทึม) และเน้นปฏิสัมพันธ์ที่มีแรงเสียดทานต่ำระหว่างกัน กรอบนี้เข้ากับแบบจำลองแพลตฟอร์มได้อย่างลงตัว ทีมแพลตฟอร์มลดภาระทางปัญญาของทีมที่จัดตามสายธารงาน เพื่อให้โฟกัสที่คุณค่าต่อผู้ใช้และทางคลินิก

Run เทียบกับ change Run คือการรักษาให้บริการที่ใช้งานอยู่ปลอดภัยและพร้อมใช้ Change คือการปรับปรุงหรือสร้างบริการ ทีมผลิตภัณฑ์ที่ทั้งสร้างและดูแลบริการ ("you build it, you run it") ปิดวงจรข้อมูลย้อนกลับและปรับปรุงความปลอดภัย แต่ต้องจัดสรรเงินให้สมดุลอย่างซื่อตรง การอดอยาก run เพื่อหาเงินให้ change คือวิธีที่ทำให้ระบบทางคลินิกเสื่อมถอย

แพลตฟอร์มที่บางที่สุดที่ใช้งานได้ (thinnest viable platform: TVP) จาก Team Topologies แพลตฟอร์มควรเป็นชุดบริการร่วมที่ เล็กที่สุด ซึ่งลดแรงเสียดทานให้ทีมสายธารงานได้จริง ไม่มากไปกว่านั้น แพลตฟอร์มที่สร้างเกินจะกลายเป็นคอขวดและระบบเก่าของตัวเอง เริ่มจากขีดความสามารถไม่กี่อย่างที่ทุกทีมต้องการจริง (การพิสูจน์ตัวตน ชั้นการทำงานร่วมกันได้ การโฮสต์ ระบบออกแบบ) และเติบโตเฉพาะเมื่อมีความต้องการที่มีหลักฐาน

แนวปฏิบัติที่ดี#

  1. ออกแบบแบบจำลองจากผลลัพธ์ลงมา ไม่ใช่จากผังองค์กรขึ้นไป เริ่มจากผลลัพธ์ของประชากรและบริการที่คุณต้องขยับ แล้วหาสายธารคุณค่าที่ส่งมอบผลลัพธ์เหล่านั้น จากนั้นจึงออกแบบทีมและเทคโนโลยี TOM ที่ยึดกับลำดับชั้นเดิมก็แค่ทำให้ไซโลปัจจุบันเป็นอัตโนมัติ

  2. ใช้รูปแบบแพลตฟอร์มบวกสหพันธ์ จัดให้มีขีดความสามารถร่วมจากส่วนกลางเป็นแพลตฟอร์มแบบบริการตนเอง และให้ทีมสายธารงานในโรงพยาบาลและพื้นที่สร้างต่อยอด วิธีนี้ให้ความสม่ำเสมอระดับชาติด้านความปลอดภัยและการทำงานร่วมกันได้ พร้อมความเร็วและความเป็นเจ้าของในท้องถิ่น ซึ่งเป็นการประสานที่โดเมนนี้ต้องการ

  3. จัดสรรเงินให้ผลิตภัณฑ์ ไม่ใช่โครงการ ย้ายเงินจากโครงการที่มีกรอบเวลาไปสู่ทีมผลิตภัณฑ์ที่ได้รับเงินทุนอย่างต่อเนื่องและจัดตามสายธารคุณค่า เงินทุนแบบโครงการบังคับให้ทีมสลายตัวในจังหวะที่เรียนรู้โดเมนได้แล้วพอดี เงินทุนแบบผลิตภัณฑ์ธำรงความรู้ด้านความปลอดภัยและการทำซ้ำเป็นรอบที่บริการสุขภาพต้องการ (ดู หัวข้อ 5.0 — การทำงานแบบยึดผลิตภัณฑ์เป็นแกน)

  4. ทำให้การควบคุมค่าใช้จ่ายเหมาะสมและเป็นขั้นตอน ใช้การจัดสรรเงินเป็นขั้นที่ผูกกับหลักฐาน คือปล่อยเงินที่ด่าน discovery, alpha, beta และ live แทนการอนุมัติทั้งโปรแกรมล่วงหน้า การควบคุมค่าใช้จ่ายแบบGDSและเส้นทางการประกันคุณภาพของ NHS มีไว้เพื่อป้องกันต้นทุนจมขนาดใหญ่กับแนวคิดที่ยังไม่พิสูจน์ ให้ใช้เป็นเกณฑ์ที่ปรับตามความเสี่ยงและคุณค่า ไม่ใช่ระบบราชการแบบเหมารวม

  5. ทำให้สิทธิ์ในการตัดสินใจชัดเจนด้วยแผนผัง RACI หรือ RAPID อำนาจที่คลุมเครือเป็นสาเหตุที่พบบ่อยที่สุดของการส่งมอบที่ติดขัด สำหรับการตัดสินใจสำคัญแต่ละประเภท ให้ระบุว่าใครรับผิดชอบ/รับผิดชอบสูงสุด/ถูกปรึกษา/ได้รับแจ้ง (RACI) หรือใครเสนอแนะ เห็นชอบ ดำเนินการ ให้ข้อมูล และตัดสินใจ (RAPID) เผยแพร่แผนผังนี้เพื่อให้ทีมเลิกส่งเรื่องขึ้นไปในการตัดสินใจที่ตนมีอำนาจทำเอง

  6. รักษาแพลตฟอร์มให้บางและขับเคลื่อนด้วยความต้องการ สร้างขีดความสามารถร่วมเฉพาะเมื่อมีสองทีมขึ้นไปที่ต้องการสิ่งเดียวกันอย่างชัดเจน และปฏิบัติต่อแพลตฟอร์มเป็นผลิตภัณฑ์ที่มีผู้ใช้ของตนเอง (ทีมภายใน) ต้านทานความอยากสร้างแพลตฟอร์มยิ่งใหญ่ไว้ล่วงหน้า แพลตฟอร์มที่บางที่สุดที่ใช้งานได้ได้ขอบเขตของมันมาจากการถูกนำไปใช้

  7. บริหารผู้จัดหาสินค้าและบริการเป็นส่วนหนึ่งของแบบจำลอง ไม่ใช่อยู่นอกแบบจำลอง ตัดสินใจอย่างตั้งใจว่าขีดความสามารถใดเป็นเชิงกลยุทธ์ (สร้าง/เป็นเจ้าของ) และอะไรเป็นสินค้าโภคภัณฑ์ (ซื้อ) หลีกเลี่ยงการผูกติดผู้จัดหารายเดียว (lock-in)กับข้อมูลทางคลินิกหลัก และกำหนดให้สัญญามีมาตรฐานเปิดและสิทธิ์ในการออก ผู้จัดหาของคุณคือชั้นหนึ่งของแบบจำลองการดำเนินงาน และวิธีการทำงานของพวกเขาต้องเข้ากันได้กับของคุณ

  8. ทำให้สิทธิ์ในการตัดสินใจชัดเจน แบบจำลองการดำเนินงานใช้ได้ก็ต่อเมื่อผู้คนรู้ว่าใครตัดสินใจอะไร ทางเลือกใดอยู่กับทีมผลิตภัณฑ์ ทางเลือกใดอยู่กับหน่วยงานกำกับความปลอดภัยทางคลินิก และทางเลือกใดต้องถึงคณะกรรมการ จัดทำแผนผังสิทธิ์ในการตัดสินใจและผลักการตัดสินใจแต่ละเรื่องลงไปยังระดับต่ำสุดที่รับไว้ได้อย่างปลอดภัย เพื่อไม่ให้การส่งมอบถูกบีบด้วยการส่งเรื่องขึ้นไปโดยไม่จำเป็น อำนาจที่คลุมเครือเป็นสาเหตุที่พบบ่อยที่สุดข้อหนึ่งของการส่งมอบที่ช้าและเอาแต่ป้องกันตัว

  9. ปฏิบัติต่อแบบจำลองการดำเนินงานเป็นผลิตภัณฑ์ที่คุณพัฒนา แบบจำลองการดำเนินงานเป้าหมายไม่ได้ตั้งไว้ครั้งเดียวแล้วใส่กรอบแขวนผนัง ให้ตรวจสอบเมื่อความต้องการ เทคโนโลยี และความเป็นพันธมิตรเปลี่ยน และปรับตามหลักฐาน เฝ้าดูสัญญาณไม่กี่อย่าง ได้แก่ การไหลของงาน เวลาในการตัดสินใจ การทำงานซ้ำ และสุขภาพของทีม และเปลี่ยนโครงสร้างเมื่อสิ่งเหล่านี้ขัดขวางอย่างเห็นได้ชัด ไม่ใช่ตามกระแสการปรับโครงสร้างองค์กร

คำถามสำหรับหารือกับทีมของคุณ#

  1. แบบจำลองการดำเนินงานของเราออกแบบจากผลลัพธ์และสายธารคุณค่าลงมา หรือเพียงทำให้ผังองค์กรเดิมและไซโลของมันเป็นอัตโนมัติ คำถามนี้ตรงกับคำเตือนหลักของหัวข้อที่ว่า TOM ที่ยึดกับลำดับชั้นปัจจุบันเพียงทำให้ไซโลที่มีอยู่ฝังแน่นยิ่งขึ้น จึงควรนำมาวางบนโต๊ะก่อนการปรับโครงสร้างใด ๆ สิ่งนี้สำคัญในบริบทสุขภาพและการดูแล เพราะสายธารคุณค่าตามเส้นทางของประชาชน คือ ส่งต่อ คัดกรอง รักษา ข้ามองค์กรที่มีอธิปไตย ขณะที่ผังองค์กรตามเขตแดนของสถาบัน และแบบจำลองที่สร้างบนอย่างหลังจะผลิตบริการที่กระจัดกระจายและทำงานร่วมกันไม่ได้ด้วยเงินสาธารณะต่อไป ความตึงเครียดที่ควรถกกันอย่างตรงไปตรงมาคือการออกแบบจากบนลงล่างตามผลลัพธ์สร้างความปั่นป่วนจริง เพราะตัดข้ามความเป็นเจ้าของของแผนก งบประมาณ และสายการรายงานที่ผู้อาวุโสสร้างอาชีพไว้รอบ ๆ ดังนั้นการทำให้ถูกต้องมีต้นทุนทางการเมืองจริง ทดสอบตนเองให้เป็นรูปธรรมโดยระบุผลลัพธ์สามอันดับแรกและไล่ดูว่าขอบเขตทีมและสายเงินจริงของคุณตามสายธารคุณค่าเหล่านั้นหรือตามแผนก หากทีมสอดคล้องกับแผนกอย่างชัดเจน นั่นคือคำตอบของคุณ คำตอบที่ดีและซื่อสัตย์ยอมรับว่าแบบจำลองมีรูปร่างตามผังองค์กรตรงไหน ระบุสายธารคุณค่าอย่างน้อยหนึ่งสายที่ถูกแบ่งข้ามไซโลจนเสียหาย และเป็นจริงเกี่ยวกับเขตแดนเชิงโครงสร้างที่องค์กรยินดีวาดใหม่

  2. อะไรควรอยู่ในแพลตฟอร์มที่บางที่สุดที่ใช้งานได้ของเรา และเราจะป้องกันไม่ให้มันถูกสร้างเกินจนเป็นคอขวด หรือสร้างน้อยเกินจนทุกทีมสร้างระบบท่อพื้นฐานเดียวกันซ้ำได้อย่างไร รูปแบบแพลตฟอร์มบวกสหพันธ์ใช้ได้ก็ต่อเมื่อแพลตฟอร์มยังบางและขับเคลื่อนด้วยความต้องการ และคำถามนี้ให้ทีมเผชิญกับรูปแบบความล้มเหลวทั้งสองที่หัวข้อระบุ คือแพลตฟอร์มยิ่งใหญ่ที่กลายเป็นคอขวดระบบเก่าของตัวเอง และการไม่มีเลยที่บังคับให้ทุกทีมสร้างล็อกอิน การเชื่อมต่อ และการตรวจสอบย้อนหลังซ้ำ สิ่งนี้สำคัญเพราะใน ICS แพลตฟอร์มคือโครงสร้างพื้นฐานร่วมโดยแท้จริง (การยืนยันตัวตน ชั้นการทำงานร่วมกันได้แบบ FHIR การโฮสต์ที่มีเกณฑ์พื้นฐานด้านความปลอดภัย ระบบออกแบบ) และการกำหนดขอบเขตผิดจะคูณต้นทุนหรือแรงเสียดทานข้ามทุกทีมสายธารงาน ข้อแลกเปลี่ยนที่ควรถกคือจังหวะและหลักฐาน สร้างเร็วเกินไปคุณจะเดาผิดและสร้างคอขวด สร้างช้าเกินไปความซ้ำซ้อนก็แข็งตัวไปแล้ว ดังนั้นเกณฑ์ "สองทีมขึ้นไปต้องการสิ่งเดียวกันอย่างชัดเจน" คือหัวใจ และทีมควรทดสอบอย่างเข้มว่าใช้เกณฑ์นี้จริงหรือแค่สร้างสิ่งที่ดูเหมือนเป็นศูนย์กลางอย่างชัดเจน ให้ดูสิ่งที่คุณถือเป็นแพลตฟอร์มในปัจจุบันเทียบกับสิ่งที่ทีมสร้างซ้ำ และถามว่าแพลตฟอร์มถูกบริหารเป็นผลิตภัณฑ์ที่มีผู้ใช้ภายในและ SLA ของตนเอง หรือเป็นคิวที่ทุกคนรอ คำตอบที่ซื่อสัตย์จะระบุขีดความสามารถเฉพาะที่ผ่านการทดสอบสองทีมในวันนี้ ต้านทานแรงล่อใจที่จะสร้างส่วนที่เหลือไว้ล่วงหน้า และให้คำมั่นว่าจะปฏิบัติต่อผู้ใช้ภายในของทีมแพลตฟอร์มเป็นลูกค้าจริงที่มีระดับการให้บริการจริง

  3. สิทธิ์ในการตัดสินใจของเราคลุมเครืออย่างแท้จริงตรงไหน และทีมกำลังส่งเรื่องขึ้นไปในเรื่องใดทั้งที่ควรมีอำนาจตัดสินใจเอง อำนาจที่คลุมเครือถูกชี้ว่าเป็นสาเหตุที่พบบ่อยที่สุดของการส่งมอบที่ติดขัด คำถามนี้จึงเผยแรงเสียดทานในชีวิตประจำวันที่แผนผัง RACI หรือ RAPID ที่เผยแพร่มีไว้เพื่อขจัด สิ่งนี้สำคัญอย่างยิ่งในระบบสุขภาพแบบสหพันธ์ที่ทีมระดับพื้นที่ คณะกรรมการดิจิทัลของ ICS ความปลอดภัยทางคลินิก และการกำกับดูแลข้อมูล ล้วนมีข้ออ้างโดยชอบธรรมต่อการตัดสินใจ และเขตแดนที่ไม่ชัดหมายถึงทุกอย่างถูกส่งขึ้นไป หรือแย่กว่านั้นคือไม่มีใครเป็นเจ้าของการตัดสินจนกว่าจะเกิดปัญหา ความตึงเครียดที่ควรสำรวจคือการมอบการตัดสินใจต้องไว้วางใจทีมภายในกรอบ ซึ่งผู้นำระดับสูงและคณะกรรมการมักต่อต้านโดยเฉพาะเมื่อเกี่ยวกับความปลอดภัยทางคลินิกหรือเงินสาธารณะ แต่การกักความไว้วางใจนั้นแหละคือสิ่งที่สร้างทางตันของการส่งเรื่องขึ้นไปตั้งแต่แรก ทำให้เป็นรูปธรรมโดยแจกแจงการตัดสินใจห้าเรื่องล่าสุดที่ถูกส่งขึ้นไป แล้วถามแต่ละเรื่องว่าใครควรเป็นผู้ตัดสินและกรอบแบบใดจะทำให้เขาตัดสินได้ รูปแบบมักเผยให้เห็นประเภทการตัดสินใจที่คลุมเครือซ้ำ ๆ จำนวนไม่มาก คำตอบที่ดีจะได้ข้อความที่เฉพาะเจาะจงและเผยแพร่ได้ว่าใครตัดสินอะไร โดยแยกมาตรฐานแพลตฟอร์ม การออกแบบบริการ และการอนุมัติความปลอดภัยทางคลินิกออกจากกัน และซื่อสัตย์ว่าการตัดสินใจใดที่องค์กรยินดีมอบให้จริงเทียบกับที่จะเก็บไว้ส่วนกลางและเพราะเหตุใด

  4. เราจัดสรรเงินให้ run และ change อย่างซื่อตรงหรือไม่ หรือกำลังเงียบ ๆ ทำให้การดำเนินงานของบริการที่ใช้งานอยู่อดอยากเพื่อจ่ายให้ฟีเจอร์ใหม่ หัวข้อนี้พูดตรง ๆ ว่าการอดอยาก run เพื่อหาเงินให้ change คือวิธีที่ทำให้ระบบทางคลินิกเสื่อมถอย และคำถามนี้บังคับให้ความสมดุลถูกเปิดเผยก่อนที่ระบบล่มหรือเหตุการณ์ด้านความปลอดภัยจะเปิดเผยแทนคุณ สิ่งนี้สำคัญในด้านสุขภาพและการดูแล เพราะ "run" ไม่ใช่ค่าใช้จ่ายหลังบ้าน แต่คือความพร้อมใช้ของระบบที่แพทย์และบุคลากรพึ่งพา ณ จุดให้การดูแล งบ run ที่ลดลงจึงปรากฏเป็นการหยุดทำงานที่อาจส่งผลต่อผู้ป่วย ไม่ใช่แค่ผู้ใช้ที่ไม่สะดวก ข้อแลกเปลี่ยนนี้อึดอัดเพราะ change มองเห็นและได้รับการเฉลิมฉลอง ขณะที่ run มองไม่เห็นจนกว่าจะล้มเหลว คณะกรรมการและโร้ดแมปจึงเอนไปทางของใหม่โดยธรรมชาติ แบบจำลอง "you build it, you run it" ช่วยโดยรักษาวงจรข้อมูลย้อนกลับให้ปิด แต่ก็ต่อเมื่อเวลา run ของทีมได้รับการปกป้องจริง ไม่ใช่จัดสรรตามชื่อแล้วถูกปล้นไป ทำให้เป็นรูปธรรมโดยดูว่าสัดส่วนกำลังของแต่ละทีมผลิตภัณฑ์ในไตรมาสที่แล้วใช้ไปกับการรักษาบริการให้ปลอดภัยและพร้อมใช้เท่าใดเทียบกับที่วางแผนไว้ และงาน run ถูกติดตามและให้คุณค่า หรือถูกมองเป็นการขัดจังหวะ คำตอบที่ซื่อสัตย์จะระบุว่า run ถูกจัดสรรเงินน้อยเกินไปตรงไหนในวันนี้ ปกป้องการจัดสรร run ที่สมจริงเป็นรายจ่ายอันดับแรกไม่ใช่เศษที่เหลือ และตรงไปตรงมาว่าบริการที่ใช้งานอยู่ใดแบกความเสี่ยงเชิงปฏิบัติการที่สะสมไว้

  5. ขีดความสามารถใดที่เราเลือกอย่างตั้งใจว่าจะสร้างและเป็นเจ้าของ เทียบกับซื้อ และเรากำลังยอมรับ lock-in กับข้อมูลทางคลินิกหลักโดยไม่ตั้งใจหรือไม่ แนวปฏิบัติที่ดีที่นี่คือตัดสินใจสร้างหรือซื้ออย่างตั้งใจ หลีกเลี่ยง lock-in กับผู้จัดหารายเดียวในข้อมูลทางคลินิกหลัก และปฏิบัติต่อผู้จัดหาเป็นชั้นหนึ่งของแบบจำลองการดำเนินงาน ไม่ใช่สิ่งที่อยู่ข้างนอก คำถามนี้ทดสอบว่าทางเลือกเหล่านั้นถูกตัดสินจริงหรือเป็นไปตามค่าเริ่มต้น สิ่งนี้สำคัญเพราะในสุขภาพดิจิทัล lock-in ที่ส่งผลมากที่สุดคือรอบเวชระเบียนและข้อมูลของมัน ซึ่งที่เก็บข้อมูลเฉพาะของผู้จัดหาโดยไม่มีทางออกที่เป็นจริงอาจขังทั้งระบบไว้ได้สิบปีและกำหนดว่าบริการปลายน้ำทุกตัวทำอะไรได้ ความตึงเครียดคือความเร็วเทียบกับทางเลือก การซื้อเร็วกว่าและมักถูกกว่าในวันนี้ โดยเฉพาะสำหรับทีมที่ตึงมือ แต่การซื้อที่สะดวกทุกครั้งโดยไม่มีมาตรฐานเปิดหรือสิทธิ์ในการออกเงียบ ๆ แคบลงซึ่งทางเลือกของวันพรุ่งนี้ และต้นทุนจะมองเห็นก็ต่อเมื่อคุณพยายามออก ทำให้เป็นรูปธรรมโดยแจกแจงขีดความสามารถหลักของคุณ ทำเครื่องหมายแต่ละข้อว่าเป็นเชิงกลยุทธ์ (สร้าง/เป็นเจ้าของ) หรือสินค้าโภคภัณฑ์ (ซื้อ) และตรวจสอบว่าสัญญาเบื้องหลังข้อที่เป็นสินค้าโภคภัณฑ์กำหนดมาตรฐานเปิด (HL7 FHIR, SNOMED CT) และสิทธิ์ในการออกที่บังคับใช้ได้จริงหรือไม่ คำตอบที่ดีจะแยกขีดความสามารถเชิงกลยุทธ์จริงไม่กี่อย่างออกจากอีกมากมายที่ซื้อได้อย่างปลอดภัย ซื่อสัตย์ว่าองค์กรถูกผูกติดกับข้อมูลทางคลินิกอยู่แล้วตรงไหน และให้คำมั่นเรื่องมาตรฐานเปิดและสิทธิ์ในการออกในสัญญาที่สำคัญที่สุด

  6. เราจะรู้ได้อย่างไรว่าแบบจำลองการดำเนินงานของเราต้องเปลี่ยน และสัญญาณใดจะบอกเรา ไม่ใช่ปรับโครงสร้างตามกระแสหรือเมื่อผู้นำคนใหม่เข้ามา หัวข้อนี้วางกรอบแบบจำลองการดำเนินงานเป็นผลิตภัณฑ์ที่คุณพัฒนาตามหลักฐาน ไม่ใช่แผนผังแขวนผนัง คำถามนี้จึงขอให้ทีมกำหนดล่วงหน้าว่าหลักฐานใดจะเป็นเหตุผลให้ปรับรูปร่างใหม่ สิ่งนี้สำคัญในด้านสุขภาพและการดูแล เพราะการปรับโครงสร้างสร้างความปั่นป่วนและแพง มันสลายความรู้ด้านโดเมนและความปลอดภัยทางคลินิกที่ได้มาอย่างยากลำบาก แต่ภาคส่วนนี้มักเกิดการเปลี่ยนโครงสร้างวนเวียนจากวงจรนโยบายและการแต่งตั้งใหม่ ไม่ใช่เพราะแบบจำลองปัจจุบันขวางทางจริง ความตึงเครียดอยู่ระหว่างเสถียรภาพกับการปรับตัว เปลี่ยนแบบจำลองง่ายเกินไปทีมก็ไม่เคยลงหลักหรือสั่งสมความเชี่ยวชาญด้านความปลอดภัย เปลี่ยนน้อยเกินไปโครงสร้างที่แข็งตัวก็บีบการไหลของงานนานหลังจากที่เลิกเข้ากับงานแล้ว ทำให้เป็นรูปธรรมโดยเลือกสัญญาณไม่กี่ตัวที่จะเฝ้าดู ได้แก่ การไหลของงาน เวลาในการตัดสินใจ การทำงานซ้ำ และสุขภาพของทีม และตกลงกันว่าการเคลื่อนไหวของตัวชี้วัดเหล่านี้ระดับใดจะกระตุ้นการออกแบบใหม่อย่างตั้งใจ เทียบกับการปรับเล็กน้อย คำตอบที่ซื่อสัตย์จะให้คำมั่นกับตัวชี้วัดนำไม่กี่ตัว แยกการเปลี่ยนแปลงที่ขับเคลื่อนด้วยหลักฐานออกจากการแสดงละครปรับโครงสร้าง และชัดเจนว่าใครรับผิดชอบการตรวจสอบแบบจำลองและลงมือเมื่อสัญญาณบอกว่ามันขัดขวางการส่งมอบ

ในทางปฏิบัติ: ตัวอย่างด้านสุขภาพและการดูแล#

ICS ที่ครอบคลุมห้าพื้นที่มีโรงพยาบาลแต่ละแห่งสร้างเครื่องมือนัดหมายสำหรับผู้ป่วยของตนเอง ต้นทุนซ้ำซ้อน ประสบการณ์แตกต่างกัน และไม่มีระบบใดแบ่งปันข้อมูลได้อย่างสะอาด ICS จึงออกแบบแบบจำลองการดำเนินงานใหม่

ICS กำหนดผลลัพธ์สามข้อ (ลดการไม่มาตามนัด ลดการรับไว้รักษาที่หลีกเลี่ยงได้ ปรับปรุงความเสมอภาคในการเข้าถึง) และสายธารคุณค่าเบื้องหลัง จากนั้นตั้งทีมแพลตฟอร์มขนาดเล็กที่เป็นเจ้าของขีดความสามารถที่บางที่สุดที่ใช้งานได้สี่อย่าง ได้แก่ การยืนยันตัวตน/ล็อกอินร่วม ชั้นการทำงานร่วมกันได้ที่ใช้ FHIR การโฮสต์ร่วมที่มีเกณฑ์พื้นฐานด้านความปลอดภัยและความปลอดภัยทางคลินิก และระบบออกแบบ แต่ละพื้นที่ยังคงมีทีมสายธารงานของตน แต่ตอนนี้สร้างบนแพลตฟอร์มแทนที่จะเริ่มจากศูนย์

เงินทุนเปลี่ยนจากการเสนอขอโครงการรายปีเป็นงบประมาณผลิตภัณฑ์ประจำสำหรับแต่ละสายธาร ปล่อยผ่านด่าน discovery/alpha/beta แผนผัง RAPID ที่เผยแพร่ทำให้ชัดว่าทีมระดับพื้นที่ตัดสินใจการออกแบบบริการของตนภายในกรอบของแพลตฟอร์มและความปลอดภัยทางคลินิก ขณะที่คณะกรรมการดิจิทัลของ ICS ตัดสินใจมาตรฐานแพลตฟอร์ม ภายในหนึ่งปี สามพื้นที่ใช้ขีดความสามารถการจองร่วมกันหนึ่งเดียว เกณฑ์พื้นฐานด้านการออกแบบและความปลอดภัยสอดคล้องกัน และฟีเจอร์ใหม่ที่เคยใช้รอบโครงการเต็ม ๆ ก็ส่งมอบได้ในไม่กี่สัปดาห์ เพราะแพลตฟอร์มรับงานหนักที่ไม่สร้างความแตกต่างไปแล้ว

มุมมองตามภาคส่วน#

แบบจำลองการดำเนินงานมีขนาดตามองค์กรที่รับใช้ ชั้นเดียวกัน ได้แก่ สายธารคุณค่า ขีดความสามารถ ทีม การกำกับดูแล แพลตฟอร์ม และผู้จัดหาสินค้าและบริการ ถูกวาดแตกต่างกันมากโดยสตาร์ทอัป องค์กรขนาดใหญ่ และหน่วยงานรัฐ

สตาร์ทอัป#

ในบริษัทสุขภาพดิจิทัลขนาดเล็ก แบบจำลองการดำเนินงานส่วนใหญ่เป็นนัย ๆ และไม่เป็นไร คือมีทีมสายธารงานหนึ่งหรือสองทีม ผู้ก่อตั้งถือสิทธิ์ในการตัดสินใจส่วนใหญ่ และไม่มีทีมแพลตฟอร์มเพราะยังไม่มีอะไรให้ทำเป็นแพลตฟอร์ม วินัยคือทำให้การตัดสินใจจริงไม่กี่เรื่องชัดเจนแต่เนิ่น ๆ เช่น สร้างหรือซื้อที่เก็บข้อมูลทางคลินิก และจะผูกมั่นกับมาตรฐานเปิดใด เพื่อไม่ให้ทางลัดของวันนี้กลายเป็น lock-in ของวันพรุ่งนี้ Run และ change อยู่ในมือเดียวกัน ความเสี่ยงคือการรักษาไฟให้ลูกค้ายุคแรกทำให้โร้ดแมปอดอยาก การแบ่งเวลาวิศวกรรมอย่างง่ายและซื่อตรงเทียบเท่างบ run ที่ได้รับการปกป้องแบบเบา ๆ ผู้จัดหาถูกเลือกเพื่อความเร็ว แต่สตาร์ทอัปควรปฏิเสธ lock-in กับข้อมูลทางคลินิกหลักอยู่ดี เพราะผู้ซื้อ NHS ในอนาคตจะเรียกร้องสิทธิ์ในการออก

ธุรกิจขนาดเล็ก#

ผู้ให้บริการรายเล็กที่ตั้งมั่นแล้ว ได้แก่ คลินิก GP ร้านขายยาชุมชน บ้านพักคนชราหรือผู้ให้บริการดูแลที่บ้าน คลินิกที่ตั้งเดียว หรือผู้จัดหาเทคโนโลยีสุขภาพรายเล็กที่พ้นช่วงก่อนมีรายได้ มีผู้ป่วยจริงและการดำเนินงานต่อเนื่อง แต่ไม่มีทีมแพลตฟอร์ม ไม่มีขีดความสามารถด้านดิจิทัลหรือไอทีโดยเฉพาะ และมีความยืดหยุ่นด้านเงินสดหรือบุคลากรน้อย แบบจำลองการดำเนินงานในที่นี้จึงเป็นชุดขีดความสามารถที่ซื้อมาเย็บรวมกันเป็นส่วนใหญ่ ทางเลือกที่ชี้ขาดจึงเป็นเรื่องผู้จัดหา คือยืนยันมาตรฐานเปิดและสิทธิ์ในการออกในระบบทางคลินิกที่คุณจัดซื้อ เพราะคุณแบกหน้าที่ด้านการทำงานร่วมกันได้และความปลอดภัยทางคลินิกเท่ากับโรงพยาบาลใหญ่ โดยไม่มีอำนาจซื้อหรือความเชี่ยวชาญภายใน Run และ change ยุบรวมอยู่กับคนไม่กี่คนที่ให้การดูแลด้วย วินัยที่ซื่อตรงจึงคือการปกป้องเวลาเล็กน้อยเพื่อให้ระบบปลอดภัยและทันสมัย แทนที่จะดับไฟอย่างเดียว สิทธิ์ในการตัดสินใจเรียบง่าย มักเป็นหุ้นส่วนหรือเจ้าของที่ตัดสินใจ แต่ก็ทำให้เลื่อนการตัดสินใจด้านดิจิทัลออกไปไม่มีกำหนดได้ง่าย คุณค่าจึงอยู่ที่การระบุไม่กี่เรื่องที่สำคัญ (ใช้เวชระเบียนใด จะเข้าร่วมแพลตฟอร์มระดับภูมิภาคร่วมใด) และตัดสินใจอย่างตั้งใจ เมื่อ ICS หรือหน่วยงานระดับชาติมีการยืนยันตัวตน การทำงานร่วมกันได้ หรือแพลตฟอร์มการออกแบบร่วมให้ การเดินที่ดีที่สุดของธุรกิจขนาดเล็กมักคือสร้างต่อยอดบนนั้นแทนที่จะประดิษฐ์ใหม่ ยืมขีดความสามารถที่ตนจัดคนเองไม่ได้

องค์กรขนาดใหญ่#

โรงพยาบาล NHS หรือ ICS คือที่ที่รูปแบบแพลตฟอร์มบวกสหพันธ์พิสูจน์คุณค่า คือองค์กรที่มีอธิปไตยซึ่งต้องรู้สึกเหมือนบริการเดียวสำหรับผู้ป่วย ปัญหาที่ยากเป็นเรื่องการเมืองพอ ๆ กับเทคนิค คือย้ายเงินจากการเสนอขอโครงการที่มีกำหนดเวลาไปสู่งบประมาณผลิตภัณฑ์ประจำ และเผยแพร่แผนผัง RACI/RAPID เพื่อให้ทีมระดับพื้นที่เลิกส่งเรื่องขึ้นไปในการตัดสินใจที่ตนเป็นเจ้าของ องค์กรเทคโนโลยีสุขภาพหรือเภสัชภัณฑ์ขนาดใหญ่มีกล้ามเนื้อวิศวกรรมแพลตฟอร์ม แต่เสี่ยงสร้างแพลตฟอร์มภายในอันยิ่งใหญ่เกินจนกลายเป็นคอขวดของตัวเอง เกณฑ์แพลตฟอร์มที่บางที่สุดที่ใช้งานได้ คือสองทีมขึ้นไปต้องการสิ่งเดียวกันอย่างชัดเจน เป็นเบรก ในระดับนี้ สิทธิ์ในการตัดสินใจและการไหลของเงินทุนคือแบบจำลองการดำเนินงาน เทคโนโลยีมักไม่ใช่ข้อจำกัด

ภาครัฐ#

หน่วยงานสาธารณะระดับชาติหรือท้องถิ่นออกแบบแบบจำลองการดำเนินงานที่องค์กรอื่นต้องอาศัยอยู่ ทางเลือกด้านมาตรฐานและแพลตฟอร์มของหน่วยงานจึงเป็นโครงสร้างพื้นฐานระดับชาติโดยเนื้อแท้ การที่ NHS England หรือ DHSC จัดให้มีชั้นการยืนยันตัวตนร่วม แกนกลางการทำงานร่วมกันได้ หรือระบบออกแบบ คือรูปแบบแพลตฟอร์มที่ใช้ในระดับประชากร และการควบคุมค่าใช้จ่ายกับด่านการประกันคุณภาพเป็นขั้นคือวิธีที่เงินสาธารณะถูกตรวจสอบ รูปแบบความล้มเหลวคือแบบจำลองรวมศูนย์ที่กลายเป็นคอขวดห่างไกล บังคับใช้วิธีแก้เดียวกับทุกบริบทท้องถิ่น วิธีแก้คือทำขีดความสามารถที่เป็นสามัญจริงเป็นแพลตฟอร์ม และมอบส่วนที่เหลือเป็นสหพันธ์ให้โรงพยาบาลและองค์กรปกครองส่วนท้องถิ่น ความรับผิดชอบต่อรัฐสภายังหมายความว่าการตัดสินใจสร้าง/ซื้อและการบริหารผู้จัดหาเป็นเรื่องที่เป็นบันทึกสาธารณะ มาตรฐานเปิดและสิทธิ์ในการออกจึงไม่เพียงรอบคอบแต่เป็นสิ่งที่คาดหวัง

รูปแบบความล้มเหลวที่พบบ่อย#

  • ทำผังองค์กรให้เป็นอัตโนมัติ ออกแบบทีมรอบแผนกที่มีอยู่แทนสายธารคุณค่า ทำให้ TOM ฝังไซโลให้แน่นขึ้น ยาแก้: ออกแบบจากผลลัพธ์และสายธารคุณค่าลงมา
  • แพลตฟอร์มที่กลายเป็นคอขวด ทีมแพลตฟอร์มกลางที่มีขอบเขตเกินจนทุกคำขอต้องเข้าคิว ยาแก้: แพลตฟอร์มที่บางที่สุดที่ใช้งานได้ ปฏิบัติเป็นผลิตภัณฑ์ที่มี SLA
  • เงินทุนแบบโครงการสำหรับงานผลิตภัณฑ์ เงินที่หมดอายุบังคับให้เกิดการยุบแล้วสร้างทีมใหม่วนไป ยาแก้: เงินทุนผลิตภัณฑ์ต่อเนื่องที่มีด่านเป็นขั้น
  • Run อดอยากเพื่อเลี้ยง change จัดสรรเงินให้การดำเนินงานบริการที่ใช้งานอยู่น้อยเกินไปจนระบบทางคลินิกเสื่อมถอย ยาแก้: จัดสรรเงินให้ run และ change อย่างชัดเจนและปกป้องงบ run
  • การตัดสินใจที่ไม่มีเจ้าของ ไม่มีใครรู้ว่าใครตัดสินใจ ทุกอย่างจึงถูกส่งขึ้นไป ยาแก้: RACI/RAPID ที่เผยแพร่
  • Lock-in โดยปริยาย ข้อมูลทางคลินิกหลักติดอยู่ในระบบเฉพาะของผู้จัดหาโดยไม่มีทางออก ยาแก้: มาตรฐานเปิดและสิทธิ์ในการออกในทุกสัญญาเชิงกลยุทธ์

แบบจำลองระดับวุฒิภาวะ#

มิติ เริ่มต้น พัฒนา ทำให้เป็นมาตรฐาน บริหารจัดการ ประสานบูรณาการ
โครงสร้าง ขับเคลื่อนด้วยผังองค์กร แยกเป็นไซโล สอดคล้องกับสายธารคุณค่าบางส่วน สร้างรูปแบบแพลตฟอร์มบวกสหพันธ์ กำกับดูแลและทบทวนขอบเขตเทียบกับตัวชี้วัดการไหลของงาน ปรับรูปร่างใหม่อย่างต่อเนื่องรอบผลลัพธ์
เงินทุน โครงการรายปี ผสมระหว่างโครงการและผลิตภัณฑ์ เงินทุนผลิตภัณฑ์ที่มีด่านเป็นขั้น ติดตามค่าใช้จ่ายและการส่งมอบเทียบกับ KPI และประกันคุณภาพของด่าน เงินทุนตามผลลัพธ์ ปล่อยตามหลักฐาน
สิทธิ์ในการตัดสินใจ คลุมเครือ ทุกอย่างถูกส่งขึ้นไป มีเอกสารบางส่วน เผยแพร่และใช้ RACI/RAPID วัดและบริหารความล่าช้าในการตัดสินใจและการส่งเรื่องขึ้นไป มอบอำนาจภายในกรอบที่ชัดเจน แทบไม่ต้องส่งเรื่องขึ้นไป
แพลตฟอร์ม ไม่มี ทุกทีมสร้างซ้ำ ชิ้นส่วนร่วมแบบเฉพาะกิจ แพลตฟอร์มที่บางที่สุดที่ใช้งานได้ ขับเคลื่อนด้วยความต้องการ ติดตาม SLA การนำไปใช้ และความน่าเชื่อถือของแพลตฟอร์มเทียบกับเป้าหมาย แพลตฟอร์มเป็นผลิตภัณฑ์ภายในที่เติบโตเต็มที่
ผู้จัดหา Lock-in การซื้อเชิงยุทธวิธี กำหนดมาตรฐานบางข้อ ตัดสินใจสร้าง/ซื้ออย่างตั้งใจ ประกันผลการดำเนินงานของผู้จัดหาและการปฏิบัติตามมาตรฐาน มาตรฐานเปิด สิทธิ์ในการออก ตลาดที่แข็งแรง

รายการตรวจสอบ#

  • แบบจำลองการดำเนินงานออกแบบจากผลลัพธ์และสายธารคุณค่า ไม่ใช่ลำดับชั้นเดิม
  • ขีดความสามารถร่วมจัดให้เป็นแพลตฟอร์มที่บางที่สุดที่ใช้งานได้ โดยทีมสายธารงานสร้างต่อยอด
  • ทีมผลิตภัณฑ์ได้รับเงินทุนต่อเนื่องและจัดตามสายธารคุณค่า
  • การควบคุมค่าใช้จ่ายเป็นขั้น (ด่าน discovery/alpha/beta/live) และเหมาะสมกับความเสี่ยงและคุณค่า
  • สิทธิ์ในการตัดสินใจมีเอกสาร (RACI หรือ RAPID) และเผยแพร่
  • Run และ change ได้รับเงินทุนอย่างชัดเจน และงบ run ได้รับการปกป้อง
  • เข้าใจและใช้ประเภททีม (stream-aligned, platform, enabling, complicated-subsystem)
  • สร้างหรือซื้อเป็นทางเลือกที่ตั้งใจต่อขีดความสามารถแต่ละอย่าง ข้อมูลทางคลินิกหลักไม่ถูก lock-in
  • สัญญากำหนดมาตรฐานเปิด (เช่น HL7 FHIR, SNOMED CT) และสิทธิ์ในการออก
